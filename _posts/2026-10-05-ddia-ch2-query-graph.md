## 오늘 공부한 것
『데이터 중심 애플리케이션 설계(DDIA)』 2장 나머지를 읽었다. 지난번에 본 지역성을 RDB 쪽에서 다시 보고, 선언형 질의가 왜 유리한지, 그리고 그래프 모델과 그래프 질의 언어 4가지(사이퍼, SQL 재귀, RDF/트리플, 데이터로그)를 정리했다.

## 내가 가졌던 질문
- 문서 DB의 지역성은 공짜인가, RDB는 지역성을 아예 못 얻나
- SQL 같은 선언형 언어가 명령형보다 나은 이유가 뭔가
- 맵리듀스는 뭐고, MongoDB는 왜 집계 파이프라인으로 갔나
- 그래프를 RDB 테이블로 표현할 수 있나
- 그래프 질의 언어들은 서로 뭐가 다른가
- RDF에 나오는 `_:someName`은 뭔가

## 1. 질의를 위한 데이터 지역성

자주 같이 쓰는 데이터를 디스크나 메모리의 물리적으로 붙어 있는 공간(블록/페이지)에 모아두는 것. 디스크 탐색 횟수가 줄어서 I/O가 빨라진다.

### 문서 모델
- 여러 테이블로 쪼개지 않고 JSON/BSON 한 덩어리로 통째로 저장한다.
- 화면에 문서 하나를 통째로 그릴 때는 추가 색인 검색이나 디스크 탐색 없이 한 번에 읽어온다.
- 대신 비용이 있다.
  - **읽기 낭비**: 필드 하나만 필요해도 문서 전체를 메모리에 올린다. 문서가 크면 손해가 크다.
  - **쓰기 낭비**: 수정으로 부호화된 크기가 바뀌면 문서 전체를 다시 써야 한다.
- 그래서 문서는 작게 유지하고, 크기가 계속 커지는 쓰기 패턴은 피해야 지역성 이점이 남는다.

### 관계형 모델
- 정규화 때문에 데이터가 여러 테이블에 흩어지고, 그만큼 색인 검색과 디스크 탐색이 늘어난다.
- 기본은 행 단위로 모든 컬럼을 묶어 저장하는 행 기반 저장소다.
- RDB도 지역성을 얻는 방법이 있다.
  1. **클러스터드 인덱스**: PK 순서대로 실제 행을 물리적으로 정렬해 둔다.
  2. **파티셔닝**: 범위나 날짜 단위로 저장 영역을 나눈다.
  3. **테이블 클러스터**: 부모 행과 자식 행을 같은 블록에 둬서 JOIN 시 디스크 이동을 없앤다.
  4. (참고) **컬럼 기반 저장소**: 분석용(OLAP)에서 같은 컬럼끼리 모아 대규모 집계를 빠르게 한다.

## 2. 선언형 질의 vs 명령형 질의

### 선언형(SQL)이 유리한 이유
- **구현 은닉**: "무엇을 원하는지"만 쓰고, 어떤 색인을 쓸지·어떤 조인 방식을 쓸지는 옵티마이저가 정한다. 엔진이 좋아져도 쿼리는 그대로 둔다.
- **순서 비의존**: 명령형 코드는 결과 순서에 기대는 경우가 있어서 DB가 레코드를 재배치하기 어렵다. SQL은 `ORDER BY`가 없으면 순서를 보장하지 않으니 DB가 내부를 자유롭게 바꿀 수 있다.
- **병렬 실행**: 요즘 CPU는 클럭보다 코어 수가 늘어난다. 결과 패턴만 정한 선언형 질의가 여러 코어·여러 노드로 나눠 돌리기 쉽다.

### 맵리듀스와 MongoDB
- **맵리듀스**: 여러 대를 묶은 클러스터에서 대량 데이터를 분산 처리하는 저수준 모델.
  - `map`: 문서마다 호출되어 키-값을 `emit`
  - `reduce`: 같은 키의 값들을 모아 결과 계산
  - 둘 다 부수 효과 없는 순수 함수여야 한다.
- 한계: 자바스크립트 함수 두 개를 직접 짜야 해서 쓰기 어렵고, 명령형 코드라 옵티마이저가 손댈 여지가 없다.
- 그래서 MongoDB는 2.2부터 SQL 비슷한 선언형 **집계 파이프라인**(`$match`, `$group` 등)을 넣었고, 맵리듀스 직접 작성은 밀려났다.

## 3. 그래프 데이터 모델

다대다 관계가 많고 계층이 복잡하게 얽혀 있을 때 쓴다.

- **정점(vertex/node)**: 개체. 예: 사람 `루시`, `알랭`, 도시 `런던`, 국가 `미국`, 대륙 `유럽`
- **간선(edge)**: 방향 있는 관계. 예: `married`, `lives_in`, `born_in`, `within`
- 사람 사이 관계와 지리적 포함 관계(`within`)처럼 성격이 전혀 다른 것도 한 그래프에 같이 넣고 계층을 따라 탐색할 수 있다.

### RDB로 그래프 표현하기 (예제 2-2)
테이블 2개면 된다.

```sql
CREATE TABLE vertices (
  vertex_id  integer PRIMARY KEY,
  properties json
);

CREATE TABLE edges (
  edge_id     integer PRIMARY KEY,
  tail_vertex integer REFERENCES vertices (vertex_id),  -- 출발
  head_vertex integer REFERENCES vertices (vertex_id),  -- 도착
  label       text,
  properties  json
);

CREATE INDEX edges_tails ON edges (tail_vertex);
CREATE INDEX edges_heads ON edges (head_vertex);
```

- 정점 1개 = `vertices` 1행, 간선 1개 = `edges` 1행.
- `tail_vertex`, `head_vertex` 양쪽에 인덱스를 걸어서 들어오는 간선과 나가는 간선을 둘 다 빠르게 따라간다.

## 4. 그래프 질의 언어 4가지

### 사이퍼 (Cypher)
Neo4j용 선언형 질의 언어. ASCII 화살표로 그래프 모양을 그대로 쓴다.
- `( )`: 정점
- `-[:관계명]->`: 방향 있는 간선
- `*0..`: 0번 이상 반복해서 따라가기 (깊이가 정해지지 않은 순회)

```cypher
MATCH
  (person) -[:BORN_IN]->  () -[:WITHIN*0..]-> (us:Location {name: 'United States'}),
  (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (eu:Location {name: 'Europe'})
RETURN person.name
```

미국에서 태어나 유럽에 사는 사람 찾기. 사람부터 훑을지, 미국/유럽 노드에서 거꾸로 따라갈지는 옵티마이저가 고른다.

### SQL 재귀 질의 (`WITH RECURSIVE`)
- 일반 `JOIN`은 몇 번 조인할지 미리 정해야 해서, 깊이가 들쭉날쭉한 계층 순회를 표현할 수 없다.
- SQL:1999의 재귀 공통 테이블 식(`WITH RECURSIVE`)으로 같은 문제를 풀 수 있다.
- 다만 사이퍼 몇 줄짜리가 SQL로는 훨씬 길고 복잡해진다.

### 트리플 저장소와 RDF
- **트리플**: 모든 정보를 `(주어, 서술어, 목적어)` 세 개로 표현한다.
  - 목적어가 값이면 속성: `(루시, 나이, 33)`
  - 목적어가 다른 정점이면 간선: `(루시, 결혼하다, 알랭)`
- **RDF**: 웹 데이터를 기계가 읽을 수 있게 엮자는 시맨틱 웹의 W3C 표준 모델.
- 표기 형식
  - **RDF/XML**: 초기 표준인데 장황하고 어려워서 사실상 안 쓰였다.
  - **Turtle (N3)**: 사람이 읽기 쉽게 줄인 텍스트 형식.
  - **JSON-LD**: 지금은 검색엔진용 메타데이터(schema.org) 쪽에서 많이 쓴다.
- **`_:someName` (공백 노드)**: 외부에서 참조하는 URI가 아니다. 파일 안에서 "이것들이 같은 정점"이라는 걸 표시하려고 붙인 지역 변수 같은 라벨이다.

### 데이터로그 (Datalog)
프롤로그 계열의 논리 질의 언어. 데이터를 찾는다기보다, 사실과 규칙에서 결론을 추론한다.
- 기본 형태: `결론 :- 조건1, 조건2.`
- **AND**: 쉼표로 조건을 잇는다. 전부 참이어야 결론이 나온다.
- **OR**: 같은 결론에 대해 규칙을 줄을 나눠 여러 개 쓴다.

```prolog
% 사실: 루시는 아이다호 출생, 아이다호는 미국 안에 있다
born_in(lucy, idaho).
within(idaho, usa).

% 규칙: Place가 Region 안에 있는가 (재귀)
in_location(Place, Region) :- within(Place, Region).
in_location(Place, Region) :- within(Place, X), in_location(X, Region).

% 질의: 미국 안에서 태어난 사람은?
?- born_in(Person, Place), in_location(Place, usa).
```

`in_location` 두 줄이 OR이다. 바로 포함되거나(1번 규칙), 한 단계 들어간 곳이 다시 포함되거나(2번 규칙). SQL로는 길어지는 재귀 탐색이 점화식처럼 두 줄로 끝난다.

## 5. 세 모델 비교

| 구분 | 문서 모델 | 관계형 모델 | 그래프 모델 |
| :--- | :--- | :--- | :--- |
| 저장 단위 | JSON/BSON 문서 하나 | 테이블의 행 | 정점과 간선 |
| 지역성 | 문서를 한 덩어리로 저장 | 클러스터드 인덱스, 파티셔닝 등으로 확보 | 간선을 따라 조인 없이 관계 탐색 |
| 잘 맞는 관계 | 일대다, 문서 단위 조회 | 일대다·다대일, 정형 트랜잭션 | 다대다, 깊이가 들쭉날쭉한 계층, 소셜·지식 그래프 |
| 질의 방식 | 집계 파이프라인 (예전엔 맵리듀스) | SQL, 가변 깊이는 `WITH RECURSIVE` | 사이퍼, SPARQL, 데이터로그 |

## 아직 헷갈리는 것 / 다음에 볼 것
- `WITH RECURSIVE`로 위 사이퍼 예제를 실제로 써보기. 얼마나 길어지는지 직접 확인하고 싶다.
- SPARQL은 이름만 나왔다. 사이퍼와 문법이 어떻게 다른지 따로 볼 것.
- 3장(저장소와 검색)에서 지역성·컬럼 저장소가 다시 나올 것 같다.

## 한 줄 요약
데이터 모델은 관계 모양에 맞춰 고르고(일대다는 문서, 다대다는 그래프), 질의는 선언형이어야 DB가 알아서 최적화하고 병렬화할 여지가 생긴다.
