## 오늘 공부한 것
9장 렌더링을 읽으며 헷갈리는 걸 하나씩 물었다. RSC payload가 뭔지에서 시작해, SSR/CSR·정적/동적 렌더링·하이드레이션·Suspense까지 이어졌다. 반복해서 걸린 건 "정적"이라는 단어가 문맥마다 다른 뜻이라는 것.

## 내가 가졌던 질문
- RSC payload가 정확히 뭐고, 개발자도구 어디서 보나
- 서버 컴포넌트가 "정적인 내용"을 처리한다는데 동적 아닌가
- SSR이랑 RSC(서버 컴포넌트)는 다른 건가
- `'use client'`/`'use server'`가 SSR/CSR 개념인가
- 정적 렌더링 = SSR? 동적 = CSR?
- 요청마다 만드는 화면은 어떤 예시인가
- 정적/동적 렌더링이면 화면이 고정/슬라이드인가, hover는 뭔가
- 클라 컴포넌트도 처음엔 SSR로 그려지나
- 하이드레이션이 뭔가
- Suspense 경계와 청크가 뭔가

## 정리 (Q&A 핵심)

### RSC payload = HTML도 JSON도 아닌 "React용 트리 직렬화"
서버 컴포넌트를 렌더한 결과를 브라우저 React에게 넘기는 전용 포맷(내부 이름 Flight). 실제로 열어보면 줄 단위 스트림이고, React 엘리먼트를 배열로 표현한다.

```
1:I["/components/LikeButton.js",["chunk123"],"LikeButton"]
0:["$","div",null,{"className":"post","children":[
     ["$","h1",null,{"children":"제목"}],
     ["$","$L1",null,{"postId":1}]
   ]}]
```

- `["$","div",null,{props}]` = React 엘리먼트 하나. `$`는 "엘리먼트야" 표시, `div`는 태그, `null`은 key, 뒤가 props.
- 서버 컴포넌트(div, h1)는 **이미 렌더된 결과**가 박히고, 클라 컴포넌트(LikeButton)는 `$L1`이라는 **"자리표시 + props + 모듈 주소"**만 박힌다. 클라 컴포넌트 JS는 따로 번들로 감.

**HTML과 다르다.** HTML은 `<div>...</div>` 통짜 문자열이라 부분 비교가 안 되는데, payload는 배열 구조라 React가 "이 부분만 바뀌었다"를 알고 부분 교체한다.

### 어디서 보나 — Preview 아니라 Response
- 링크로 페이지 이동하면 네트워크 탭에 `?_rsc=...` 붙은 요청이 뜨고, 그 **Response** 탭에 payload가 있다. Preview는 못 알아봐서 비어 보인다.
- **첫 로드**는 별도 요청이 아니라, HTML 안 `<script>self.__next_f.push(...)</script>`에 payload가 동봉돼서 온다.

### "정적인 내용" = 안 변하는 게 아니라 "상호작용이 없는" 것
서버 컴포넌트가 "정적"이라는 건 데이터가 고정이란 뜻이 아니다. **클릭·상태 같은 상호작용이 없다**는 뜻. 데이터는 얼마든지 동적으로 가져온다.

```jsx
async function PostPage() {
  const post = await db.post.find(1);   // 데이터는 동적(매번 최신 가능)
  return (
    <article>
      <h1>{post.title}</h1>   {/* 그냥 보여주기 = 정적 UI */}
      <LikeButton id={1} />   {/* 상호작용 = 여기부터 클라 컴포넌트 */}
    </article>
  );
}
```

### SSR과 RSC는 다른 층 (Next는 둘을 겹쳐 씀)
| | SSR | 서버 컴포넌트/RSC |
|---|---|---|
| 뭘 위해 | 첫 화면 빨리(+SEO) | JS를 브라우저로 안 보냄 + 서버 자원 직접 |
| 결과물 | HTML | RSC payload |
| 그 JS 브라우저로 | 감(하이드레이션용) | 안 감 |

"서버가 미리 렌더해 빠른 UI"라는 겉보기는 SSR 맞다. 근데 서버 컴포넌트는 거기에 **"JS 배송을 잘라내는"** 일을 하나 더 얹는다. 그래서 "서버 컴포넌트 렌더링 과정" = RSC 렌더 + SSR + 하이드레이션 묶음이고, 그중 "빠른 UI" 부분만 떼면 SSR이다(포함 관계지 등호 아님).

### `'use client'`/`'use server'`는 SSR/CSR 개념이 아니다 — 세 축
```
'use client' / (기본=서버 컴포넌트)  → 컴포넌트 종류 (JS 브라우저로 가냐, 상호작용 되냐)
'use server'                        → 함수(서버 액션), 렌더링 무관
SSR / CSR / SSG                     → 렌더링 방식 (결과를 어디서·언제 HTML로)
```
`'use client'`의 반대는 `'use server'`가 아니라 "아무것도 안 붙임". 그리고 **`'use client'` ≠ CSR** — 클라 컴포넌트도 첫 로드엔 서버에서 SSR 된다. 이름이 "client"라서 브라우저 전용처럼 들리지만, "브라우저에서도(상호작용) 돈다"는 뜻이지 "브라우저에서만"이 아니다.

### 정적/동적 렌더링 = SSG/SSR, CSR은 별개 축
```
서버가 HTML 만든다
├─ 미리(빌드/캐시) 만듦   = 정적 렌더링  ≈ SSG/ISR
└─ 요청마다 새로 만듦     = 동적 렌더링  ≈ SSR
서버가 HTML 안 만든다
└─ 브라우저가 JS로 만듦   = CSR  (이 축 밖)
```
그래서 "정적 렌더링 = SSR?" → 아니, SSG에 가깝다. "동적 = CSR?" → 아니, SSR에 가깝고 CSR은 둘 다 아니다. 정적/동적 렌더링은 둘 다 "서버가 HTML을 언제 굽냐"의 하위 구분이고, CSR은 "서버가 안 굽는다"라 애초에 이 질문 밖.

### 동적 렌더링 예시 + 동적 API
요청마다 만드는 화면 = **사람마다·입력마다·매 순간 달라서 하나로 미리 못 만드는 것**.

| 화면 | 왜 요청마다 | 트리거(동적 API) |
|---|---|---|
| 마이페이지 | 사람마다 다름 | `cookies()` |
| 장바구니 | 내 것만 | `cookies()` |
| 검색 결과 | `?q=`마다 다름 | `searchParams` |
| 관리자 페이지 | 권한·내용 다름 | `cookies()`/`headers()` |

`cookies()`·`headers()`·`searchParams`는 "요청이 와야만 아는 값"이라, 읽는 순간 그 페이지가 자동으로 동적 렌더링으로 전환된다. (Next 15부터 `cookies()`/`headers()`/`params`/`searchParams`가 async라 `await` 필요)

### 정적/동적 렌더링은 화면 움직임과 무관
또 "정적"에 걸린 지점. 정적/동적 렌더링은 "서버가 HTML을 언제 굽냐"지, hover·슬라이드·애니메이션이 아니다.
```
대시보드 숫자 표  : 화면 안 움직임 인데 → 사람마다 다름 → 동적
블로그 이미지 슬라이드 : 막 움직임    인데 → 누구나 같음 → 정적
```
hover는 그냥 CSS `:hover`(브라우저)라 렌더링 방식과 0 상관.

### 하이드레이션 = 죽은 HTML에 JS를 부어 살리기
SSR이 뿜은 HTML은 보이긴 하는데 죽어있다(버튼 눌러도 무반응). 브라우저가 JS를 받아 React를 다시 돌려서 그 HTML에 이벤트·상태를 붙이는 게 하이드레이션.

```
① 서버 SSR → <button>♡</button> HTML (화면에 보임)
② 이 순간 onClick 안 붙음 → 눌러도 무반응 (죽은 HTML)
③ 브라우저가 JS 받고 하이드레이션 → onClick·useState 연결 → 살아남
```

- DOM은 이미 SSR이 만들어놨고, 하이드레이션은 그 **기존 DOM에 생명(이벤트/상태)을 붙이는** 것. 새로 안 그림. 단 "그냥 딸깍"이 아니라 컴포넌트 코드를 브라우저에서 다시 실행해 뭘 붙일지 파악한 뒤 붙인다 → JS 무거우면 "보이는데 안 눌리는 죽은 구간"이 길어짐.
- **서버 컴포넌트는 하이드레이션 안 함**(JS가 안 가니까). 클라 컴포넌트만 대상.
- `'use client'`는 하이드레이션의 "스위치(신청서)"고, 하이드레이션은 그 결과로 일어나는 "동작". 등호가 아니라 원인→결과(스위치 누르면 불 켜짐, 스위치=불은 아님).
- `useState`/`onClick`을 서버 컴포넌트에 쓰면 빌드 에러 나는 이유도 이거 — 서버 컴포넌트는 하이드레이션 대상이 아니라 이벤트를 붙일 기회 자체가 없다(타이밍 문제가 아니라 자격 문제. 기다린다고 발급 안 됨).

### 클라 컴포넌트도 첫 로드는 SSR
| | 첫 로드 렌더 | 하이드레이션 | 이후 상호작용 |
|---|---|---|---|
| 서버 컴포넌트 | 서버(SSR) | ❌ | ❌ |
| 클라 컴포넌트 | **서버(SSR)** | ✅ | ✅ 브라우저(CSR) |

첫 로드 땐 클라 컴포넌트까지 서버에서 HTML로 그려 "빈칸 없는 첫 화면"을 보낸다(정적 HTML 미리보기 = 하이드레이션 전 정지 사진). 그 다음 React가 **RSC payload를 설계도 삼아** HTML DOM과 맞춰 클라 컴포넌트를 하이드레이션한다. payload는 HTML에 데이터를 넣는 게 아니라, "어디가 클라 컴포넌트고 props·트리 구조가 뭔지"를 알려주는 참조본.

### Suspense 경계 + 청크 = 되는 것부터 먼저
`<Suspense fallback={...}>`로 감싼 영역이 "여기서 끊어도 되는" 경계. 안쪽이 준비 안 됐으면 fallback 먼저, 준비되면 교체.

```jsx
<Header />                          {/* 빠름 → 바로 뜸 */}
<Suspense fallback={<p>불러오는 중…</p>}>
  <SlowComments />                  {/* 느림 → 준비되면 채움 */}
</Suspense>
```

- **청크** = 응답을 한 방에 안 보내고 되는 대로 나눠 흘려보내는 조각(스트리밍). 요청은 한 번이고, 그 응답 본문이 시간차로 도착.
- **경계는 "자리(어디서 끊을지)"**, 실제로 끊기는 "시점(언제)"은 데이터가 준비된 때가 정한다. 경계 = 미리 그은 재봉선, 데이터 준비 = 실제로 자르는 순간.
- payload에서 `$L5`로 자리 잡고 뒤에 `5:...` 줄이 추가로 오는 게 이거.

## 아직 헷갈리는 것 / 다음에 볼 것
- payload를 React가 DOM과 매칭(reconcile)하는 세부 과정.
- Suspense fallback을 잘못 짜서 깜빡이는 안티패턴 사례.
- 정적/동적 렌더링을 실무에서 언제 강제(force-dynamic/force-static)하나.

## 한 줄 요약
Next 렌더링은 "정적"이라는 단어가 문맥마다 다르다는 게 함정이다 — **서버 컴포넌트의 정적 = 상호작용 없음**, **정적 렌더링 = 빌드 때 미리(SSG)**, **정적 HTML 미리보기 = 하이드레이션 전 정지 사진**. RSC payload는 HTML이 아니라 React용 트리 설계도이고, 첫 로드엔 클라 컴포넌트까지 SSR로 HTML을 그린 뒤 payload를 참조해 하이드레이션(죽은 HTML에 JS 부어 살리기)하며, Suspense 경계로 끊어 청크 단위로 스트리밍한다.
