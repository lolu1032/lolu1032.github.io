## 1. 트랜잭션의 '격리(Isolation)'란 무엇인가?

데이터베이스에서 트랜잭션(Transaction)은 논리적인 작업의 최소 단위입니다. ACID 특성 중 **I(Isolation, 격리성)** 는 여러 개의 트랜잭션이 동시에(Concurrent) 실행될 때, 각 트랜잭션이 마치 혼자서 데이터베이스를 사용하고 있는 것처럼 독립적으로 동작하도록 보장하는 성질입니다.

### 동시성의 필요성

실무에서는 수많은 사용자의 요청을 동시에 처리해야 하므로 트랜잭션들이 시간적으로 겹쳐서 실행됩니다. 한 사용자가 결제하는 동안 다른 사용자가 상품 목록을 조회하고, 또 다른 사용자가 재고를 변경하는 일이 매초 일어납니다.

### 격리의 딜레마

만약 완벽한 격리를 위해 모든 트랜잭션을 하나씩 순차적으로(Serial) 실행한다면 데이터 정합성은 완벽하겠지만, 데이터베이스의 전체 처리량(Throughput)이 급격히 떨어져 서비스가 느려집니다.

### 타협점의 탄생

성능을 높이기 위해 "어느 정도의 데이터 불일치(이상 현상)는 허용하고, 대신 동시 처리 성능을 챙기자"라는 취지로 만들어진 규칙이 바로 **격리 수준(Isolation Level)** 입니다.

즉, 격리 수준은 "정합성을 얼마나 강하게 지킬 것인가"를 단계별로 선택할 수 있게 해주는 장치입니다.

## 2. 동시 실행 시 발생하는 이상 현상(Anomalies) 총정리

격리가 제대로 지켜지지 않을 때 발생하는 버그들은 크게 **SQL 표준(1992)이 정의한 전통적인 현상**과, 이후 **비판 논문(1995)에서 추가로 지적된 현상**으로 나뉩니다.

| 구분 | 이상 현상 | 한 줄 요약 |
| :--- | :--- | :--- |
| SQL 표준 | 더티 리드(Dirty Read) | 커밋되지 않은 값을 읽는다 |
| SQL 표준 | 반복 읽기 불가능(Non-Repeatable Read) | 같은 행을 두 번 읽었는데 값이 달라진다 |
| SQL 표준 | 유령 읽기(Phantom Read) | 같은 조건으로 조회했는데 행의 개수가 달라진다 |
| 비판 논문 | 더티 라이트(Dirty Write) | 커밋되지 않은 값을 덮어쓴다 |
| 비판 논문 | 유실된 갱신(Lost Update) | 먼저 커밋한 수정이 사라진다 |
| 비판 논문 | 읽기 스큐(Read Skew) | 서로 연관된 데이터를 일관성 없게 읽는다 |
| 비판 논문 | 쓰기 스큐(Write Skew) | 각각은 규칙을 지켰는데 전체 제약이 깨진다 |

### 2.1. SQL 표준(1992)이 정의한 대표적 이상 현상 3가지

#### 더티 리드 (Dirty Read)

**정의:** 아직 커밋되지 않은(Uncommitted) 변경 데이터를 다른 트랜잭션이 읽는 현상입니다.

| 시점 | 트랜잭션 A | 트랜잭션 B |
| :--- | :--- | :--- |
| 1 | `UPDATE accounts SET balance = 0 WHERE id = 1` (미커밋) | |
| 2 | | `SELECT balance FROM accounts WHERE id = 1` → `0` |
| 3 | `ROLLBACK` | |
| 4 | | B는 존재하지 않아야 할 `0`을 기준으로 연산을 계속함 |

트랜잭션 A가 데이터를 수정하고 커밋하지 않은 상태에서 트랜잭션 B가 그 데이터를 읽습니다. 이후 트랜잭션 A가 오류로 인해 롤백(Abort)되면, 트랜잭션 B는 세상에 존재하지 않아야 할 유효하지 않은 데이터를 기반으로 연산을 수행하게 됩니다.

#### 반복 읽기 불가능 (Non-Repeatable Read / Fuzzy Read)

**정의:** 하나의 트랜잭션 내에서 같은 데이터를 두 번 읽었는데 그 사이에 값이 달라지는 현상입니다.

| 시점 | 트랜잭션 A | 트랜잭션 B |
| :--- | :--- | :--- |
| 1 | `SELECT balance ...` → `10` | |
| 2 | | `UPDATE accounts SET balance = 50 ...; COMMIT` |
| 3 | `SELECT balance ...` → `50` | |

트랜잭션 A가 특정 데이터를 읽었습니다(X = 10). 그 사이 트랜잭션 B가 그 값을 수정하고 커밋해 버렸습니다(X = 50). 트랜잭션 A가 다시 같은 데이터를 읽었을 때 값이 달라져 로직에 혼선이 생깁니다.

#### 유령 읽기 (Phantom Read)

**정의:** 같은 조건으로 데이터를 두 번 조회했는데, 중간에 다른 트랜잭션이 새로운 데이터를 추가(Insert)하거나 삭제하여 조회 결과의 행(Row) 개수가 달라지는 현상입니다.

| 시점 | 트랜잭션 A | 트랜잭션 B |
| :--- | :--- | :--- |
| 1 | `SELECT COUNT(*) ... WHERE status = 'READY'` → `1` | |
| 2 | | `INSERT INTO orders(status) VALUES ('READY'); COMMIT` |
| 3 | `SELECT COUNT(*) ... WHERE status = 'READY'` → `2` | |

반복 읽기 불가능이 **이미 존재하는 행의 값**이 바뀌는 문제라면, 유령 읽기는 **조건에 맞는 행의 집합 자체**가 바뀌는 문제입니다.

### 2.2. 비판 논문(1995)이 추가로 지적한 심각한 이상 현상들

1995년 Berenson 등이 발표한 **"A Critique of ANSI SQL Isolation Levels"** 논문은 SQL 표준의 격리 수준 정의가 불완전하다는 점을 지적하며 다음과 같은 이상 현상들을 추가로 정리했습니다.

#### 더티 라이트 (Dirty Write)

**정의:** 아직 커밋되지 않은 다른 트랜잭션의 수정 데이터를 그대로 덮어써 버리는 현상입니다.

| 시점 | 트랜잭션 A | 트랜잭션 B |
| :--- | :--- | :--- |
| 1 | `UPDATE x = 1` (미커밋) | |
| 2 | | `UPDATE x = 2` (A의 미커밋 값을 덮어씀) |
| 3 | `ROLLBACK` | |
| 4 | | B의 커밋 결과가 A의 롤백에 휘말리거나, 의도하지 않은 값이 남음 |

**문제점:** 롤백 과정에서 데이터 정합성이 치명적으로 깨지므로, 어떤 격리 수준이든 **무조건 방어해야 하는 필수 대상**입니다. 실제 대부분의 DBMS는 Read Uncommitted에서도 더티 라이트를 허용하지 않습니다.

#### 유실된 갱신 (Lost Update)

**정의:** 두 트랜잭션이 동시에 같은 데이터를 수정하려 할 때, 먼저 커밋된 트랜잭션의 수정 내용이 뒤에 커밋된 트랜잭션에 의해 완전히 지워져 버리는 현상입니다.

| 시점 | 트랜잭션 A | 트랜잭션 B |
| :--- | :--- | :--- |
| 1 | `SELECT balance` → `100` | |
| 2 | | `SELECT balance` → `100` |
| 3 | `UPDATE balance = 110; COMMIT` | |
| 4 | | `UPDATE balance = 120; COMMIT` (A의 +10이 사라짐) |

예를 들어 동시 계좌 입금 시 한쪽 금액이 증발하는 현상입니다. 두 트랜잭션 모두 같은 초깃값 `100`을 읽고 각자 계산한 뒤 덮어썼기 때문에, 나중에 커밋한 쪽의 값만 남습니다.

#### 읽기 스큐 (Read Skew)

**정의:** 연관된 데이터(예: A 계좌, B 계좌)를 읽을 때 다른 트랜잭션이 중간에 끼어들어 일관성이 깨진 상태의 데이터를 읽게 되는 현상입니다.

| 시점 | 트랜잭션 A | 트랜잭션 B |
| :--- | :--- | :--- |
| 1 | `SELECT balance FROM accounts WHERE id = 'A'` → `100` | |
| 2 | | A → B로 `50` 이체; `COMMIT` |
| 3 | `SELECT balance FROM accounts WHERE id = 'B'` → `150` | |

A 계좌는 이체 전 값(`100`), B 계좌는 이체 후 값(`150`)을 읽어서 총합이 `250`이 됩니다. 실제 총합은 `200`이어야 하므로, 트랜잭션 A는 존재한 적 없는 상태를 관측한 셈입니다.

#### 쓰기 스큐 (Write Skew)

**정의:** 개별 트랜잭션은 자체 규칙을 위반하지 않았으나, 동시에 실행되고 나니 시스템 전체의 제약 조건이 깨져버리는 현상입니다.

예를 들어 "당직 의사는 최소 1명 이상이어야 한다"는 규칙이 있고, 현재 당직 의사가 2명이라고 해봅시다.

| 시점 | 트랜잭션 A | 트랜잭션 B |
| :--- | :--- | :--- |
| 1 | `SELECT COUNT(*) ... WHERE on_call = true` → `2` | |
| 2 | | `SELECT COUNT(*) ... WHERE on_call = true` → `2` |
| 3 | 의사 1의 당직을 해제; `COMMIT` | |
| 4 | | 의사 2의 당직을 해제; `COMMIT` |

각 트랜잭션은 "아직 2명이니까 한 명을 빼도 된다"고 판단했지만, 둘 다 커밋되고 나면 당직 의사가 0명이 되어 제약 조건이 깨집니다. 잔고의 총합이 항상 일정 금액 이상이어야 하는 규칙에서도 같은 문제가 발생할 수 있습니다.

## 3. SQL 표준 4가지 격리 수준 (Isolation Level)

데이터베이스는 위와 같은 이상 현상들을 어느 선까지 허용할 것인가에 따라 4단계의 격리 수준을 제공합니다.

| 격리 수준 | 더티 리드 | 반복 읽기 불가능 | 유령 읽기 | 동시성 | 정합성 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Read Uncommitted** | 발생 | 발생 | 발생 | 최고 | 최저 |
| **Read Committed** | 차단 | 발생 | 발생 | 높음 | 중간 |
| **Repeatable Read** | 차단 | 차단 | 표준상 발생* | 중간 | 높음 |
| **Serializable** | 차단 | 차단 | 차단 | 낮음 | 최고 |

\* MySQL InnoDB의 Repeatable Read는 MVCC와 넥스트 키 락(Next-Key Lock)을 조합해 유령 읽기를 상당 부분 막지만, SQL 표준의 정의만 놓고 보면 유령 읽기까지 완전히 차단하는 수준은 Serializable입니다.

### 각 격리 수준의 특징

1. **Read Uncommitted**: 가장 느슨한 수준입니다. 동시성은 최고지만 정합성은 최악이라 실무에서 거의 사용하지 않습니다. PostgreSQL처럼 이 수준을 요청해도 내부적으로 Read Committed로 동작시키는 DB도 있습니다.
2. **Read Committed**: 더티 리드를 방지합니다. 대다수 RDB의 기본값이며, 대부분의 웹 애플리케이션에 무난한 선택입니다.
3. **Repeatable Read**: 반복 읽기 불가능을 방지합니다. MySQL InnoDB의 기본값으로 널리 알려져 있습니다.
4. **Serializable**: 모든 이상 현상을 차단합니다. 트랜잭션을 순차 실행한 것과 동일한 결과를 보장하지만, 락 대기와 직렬화 실패(Serialization Failure)가 늘어나 성능 저하가 발생할 수 있습니다.

### 데이터베이스별 기본 격리 수준

| 데이터베이스 | 기본 격리 수준 | 특징 |
| :--- | :--- | :--- |
| MySQL InnoDB | Repeatable Read | MVCC + 넥스트 키 락 |
| PostgreSQL | Read Committed | 문장 단위 스냅샷, Serializable은 SSI |
| Oracle | Read Committed | 문장 단위 일관성 읽기 |
| SQL Server | Read Committed | 기본적으로 락 기반 제어 |

> **중요:** 내가 사용하는 DB의 기본 격리 수준이 무엇인지, 그리고 그 수준이 실제로 어떤 이상 현상을 막아주는지는 반드시 확인해야 합니다. 같은 이름의 격리 수준이라도 DB마다 구현 방식과 세부 동작이 다를 수 있습니다.

## 4. 데이터베이스가 격리를 구현하는 두 가지 핵심 메커니즘

관계형 데이터베이스는 위 수준들을 구현하기 위해 크게 **락(Lock) 기반 제어**와 **MVCC(다중 버전 동시성 제어)** 를 사용합니다.

### 4.1. 락(Lock) 기반 격리 (비관적 접근)

**철학:** "언제 충돌이 날지 모르니 아예 잠궈버리자!"

데이터를 읽거나 쓸 때 **공유 락(Shared Lock)** 이나 **배타 락(Exclusive Lock)** 을 걸어 다른 트랜잭션의 접근을 물리적으로 차단합니다.

- **공유 락(S-Lock)**: 여러 트랜잭션이 동시에 읽을 수는 있지만, 쓰기는 막습니다.
- **배타 락(X-Lock)**: 읽기와 쓰기 모두 막습니다.
- **2단계 락킹(2PL)**: 트랜잭션이 락을 획득하는 단계와 해제하는 단계를 분리해 직렬 가능성을 보장하는 기법입니다.

대표적인 예시는 다음과 같습니다.

```sql
-- 비관적 락: 조회 시점부터 해당 행을 잠금
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

COMMIT;
```

MySQL InnoDB는 여기에 **넥스트 키 락(Next-Key Lock)** 을 추가로 사용합니다. 이는 레코드 락과 갭 락(Gap Lock)을 결합한 형태로, `SELECT ... FOR UPDATE`나 `UPDATE`가 범위를 스캔할 때 유령 삽입까지 막는 데 도움을 줍니다.

**단점:** 락을 기다리는 시간이 길어져 동시 처리 성능(Throughput)이 떨어질 수 있고, 두 트랜잭션이 서로의 락을 기다리는 **교착 상태(Deadlock)** 가 발생할 수 있습니다. DBMS는 보통 교착 상태를 감지해 한쪽 트랜잭션을 강제로 롤백합니다.

### 4.2. 다중 버전 동시성 제어 (MVCC & Snapshot Isolation)

**철학:** "읽는 사람과 쓰는 사람이 서로를 방해하지 않게 하자!"

데이터를 덮어씌우는 대신, 수정될 때마다 이전 버전의 데이터를 **언두 로그(Undo Log)** 등에 보존하여 여러 버전을 유지합니다.

- **읽기 트랜잭션**: 락을 걸지 않고, 자신의 트랜잭션이 시작된 시점(또는 문장이 시작된 시점)의 과거 스냅샷을 읽습니다.
- **쓰기 트랜잭션**: 충돌이 발생할 경우 먼저 커밋한 쪽만 승리(First-committer-wins)하게 만들어 유실된 갱신을 방지합니다.

MVCC를 사용하면 읽기와 쓰기가 서로를 막지 않아 동시성이 크게 향상됩니다. 하지만 **스냅샷 격리(Snapshot Isolation)** 가 곧 완벽한 직렬 가능성(Serializability)을 의미하지는 않습니다.

> **주의: 스냅샷 격리와 쓰기 스큐**
>
> 스냅샷 격리는 더티 리드, 반복 읽기 불가능, 유령 읽기, 유실된 갱신을 막아주지만, 서로 다른 행을 수정하는 **쓰기 스큐(Write Skew)** 는 막지 못할 수 있습니다. 그래서 PostgreSQL의 Serializable은 **직렬화 가능 스냅샷 격리(SSI, Serializable Snapshot Isolation)** 를 사용해 쓰기 스큐까지 감지하고, 충돌 시 트랜잭션을 직렬화 실패로 롤백합니다.

### 락 기반 vs MVCC 비교

| 구분 | 락 기반 제어 | MVCC |
| :--- | :--- | :--- |
| 읽기 방식 | 락을 획득하고 읽음 | 스냅샷을 읽음 |
| 읽기/쓰기 충돌 | 락 대기 발생 | 대기 없이 읽기 가능 |
| 쓰기 충돌 | 락 대기 또는 교착 상태 | 버전 충돌 감지 후 재시도 |
| 대표 기능 | `SELECT ... FOR UPDATE`, 넥스트 키 락 | 언두 로그, 스냅샷, SSI |
| 주의할 점 | 교착 상태, 처리량 저하 | 쓰기 스큐, 긴 트랜잭션의 언두 로그 증가 |

실제 DBMS는 둘 중 하나만 쓰기보다, 상황에 따라 두 방식을 조합합니다. MySQL InnoDB도 MVCC를 사용하면서 동시에 넥스트 키 락을 함께 사용합니다.

## 5. 애플리케이션 레벨 동시성 vs 데이터베이스 레벨 동시성

### 5.1. 자바 `synchronized` (애플리케이션 레벨)

단일 JVM(서버 1대) 내부의 스레드 간 동시성 제어에는 유용합니다. 하지만 다음과 같은 한계가 있습니다.

- **분산 환경에서 동작하지 않음**: 쿠버네티스 환경처럼 여러 대의 파드(Pod)로 스케일 아웃되면 서버마다 JVM이 따로 존재하므로, `synchronized` 락이 서버 간에 공유되지 않습니다.
- **DB 트랜잭션 경계와 무관함**: 애플리케이션 락이 걸려 있어도 다른 경로(배치, 외부 시스템, 다른 서비스)에서 DB를 직접 수정하면 막을 수 없습니다.
- **락 범위가 넓어짐**: 임계 구역이 길어지면 해당 인스턴스의 처리량이 급격히 떨어집니다.

### 5.2. 데이터베이스 Serializable 및 락/분산 락

서버가 몇 대이든, 어떤 클라이언트에서 접근하든 데이터베이스 엔진 관점에서 트랜잭션을 통제할 수 있습니다.

- **DB 격리 수준**: `SERIALIZABLE`을 사용하면 DB가 직렬 가능성을 보장합니다. 대신 직렬화 실패가 발생할 수 있으므로 애플리케이션에서 재시도 로직이 필요합니다.
- **비관적 락**: `SELECT ... FOR UPDATE`로 충돌 가능성이 높은 데이터를 미리 잠급니다.
- **낙관적 락**: 버전(`version`) 컬럼을 두고, 커밋 시점에 버전이 바뀌었는지 확인합니다. 충돌이 드물 때 유리합니다.
- **분산 락**: Redis(예: Redisson)나 DB 기반 락을 사용해 여러 서버가 하나의 자원에 동시에 접근하지 못하게 합니다. 다만 락 만료, 네트워크 분할, 긴 GC pause 같은 실패 시나리오를 반드시 고려해야 합니다.

### 상황별 실무 선택 가이드

| 상황 | 추천 접근 |
| :--- | :--- |
| 재고 감소, 쿠폰 발급처럼 단순 증감 | `UPDATE ... SET stock = stock - 1 WHERE stock > 0` 같은 원자적 SQL |
| 읽고 계산한 뒤 쓰는 복잡한 로직 | `SELECT ... FOR UPDATE` 또는 낙관적 락 + 재시도 |
| 여러 서버에서 단 한 번만 실행되어야 하는 작업 | 분산 락 + 멱등성 키 + DB 유니크 제약 |
| 금융 거래처럼 강한 정합성이 필요한 경우 | `SERIALIZABLE` + 직렬화 실패 재시도 |
| 읽기 성능이 중요한 조회 | MVCC 스냅샷 읽기 활용, 트랜잭션은 짧게 유지 |

> 분산 락은 만능 해결책이 아닙니다. 락을 획득한 서버가 멈추거나 네트워크가 분리되면 락이 풀리지 않거나 중복 실행될 수 있습니다. 가능하면 **DB의 유니크 제약 조건**과 **멱등성 키**를 마지막 안전장치로 함께 두는 것이 좋습니다.

## 6. 실무 체크리스트

동시성 이슈를 예방하려면 코드를 작성할 때 다음 항목을 점검하는 습관이 좋습니다.

- [ ] 사용하는 DB의 기본 격리 수준과 실제 동작을 알고 있는가?
- [ ] 트랜잭션 범위가 불필요하게 길지 않은가?
- [ ] 읽고-계산하고-쓰는 로직에 락이나 원자적 SQL이 적용되어 있는가?
- [ ] 교착 상태나 직렬화 실패 발생 시 재시도 로직이 있는가?
- [ ] 분산 환경에서 `synchronized`나 로컬 캐시 락에 의존하고 있지 않은가?
- [ ] 중복 요청을 막을 멱등성 키나 유니크 제약 조건이 있는가?
- [ ] 락 대기 시간과 교착 상태를 모니터링하고 있는가?

## 💡 요약 및 마무리

트랜잭션 격리 수준과 동시성 제어는 시스템의 성능과 데이터 정합성 사이의 타협점입니다.

- **Read Uncommitted**는 거의 쓰지 않고, **Read Committed**는 대다수 서비스의 무난한 기본값입니다.
- **Repeatable Read**는 같은 행의 반복 읽기를 보장하지만, DB 구현에 따라 유령 읽기와 쓰기 스큐를 주의해야 합니다.
- **Serializable**은 가장 강력하지만, 성능 저하와 직렬화 실패에 대한 재시도 설계가 필요합니다.
- **MVCC**는 읽기와 쓰기의 충돌을 줄여주지만, 스냅샷 격리가 항상 직렬 가능성을 보장하지는 않습니다.
- 분산 환경에서는 애플리케이션 로컬 락만으로는 부족하므로, DB 락·분산 락·유니크 제약·멱등성 설계를 조합해야 합니다.

내가 사용하는 데이터베이스(예: MySQL의 Repeatable Read 기본값 등)의 동작 방식을 정확히 이해하고 있어야, 선착순 이벤트나 결제 시스템 등 동시성 이슈가 민감한 서비스에서 치명적인 버그를 예방할 수 있습니다.
