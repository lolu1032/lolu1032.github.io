## 정리 (Q&A 핵심)

### SMTP는 그냥 텍스트 대화다

Simple Mail Transfer Protocol. 메일 서버끼리 쓰는 대화 규칙이고, 사람이 손으로 칠 수 있을 정도로 단순하다. 실제로 네이버 MX에 붙어봤다.

```
$ printf 'EHLO test.example.com\r\nQUIT\r\n' | nc -w 8 mx1.mail.naver.com 25

220 mx.naver.com ESMTP 1XsJsKKKSK+uOIF0t3-RxA - nsmtp
250-mx.naver.com Pleased to meet you
250-SIZE 41943040
250-8BITMIME
250-PIPELINING
250-SMTPUTF8
250-STARTTLS
250 ENHANCEDSTATUSCODES
221 2.0.0 Closing connection
```

`EHLO`로 인사하면 서버가 "나 이런 기능 됨" 하고 목록을 뱉는다. 이게 문서에서 말한 **ESMTP 확장**이다. (한글 문서에 "SMTP 확장자"라고 되어 있어서 파일 확장자인 줄 알았는데 프로토콜 확장이었다.)

- `SIZE` — 최대 메시지 크기
- `8BITMIME` — 한글 등 8비트 문자 그대로 전송
- `PIPELINING` — 명령어 왕복 없이 몰아서 전송
- `SMTPUTF8` — 이메일 주소에 한글 가능
- `STARTTLS` — 평문 연결을 암호화로 승격

HTTP와 비교하면 방향이 반대다. HTTP는 내가 서버에서 가져오고(pull), SMTP는 서버가 서버에게 밀어넣는다(push). 그래서 실패했을 때 처리도 다르다. HTTP는 500 뜨면 끝이지만, 메일은 큐에 넣고 며칠간 재시도한다.

### 제출(submission)과 전송(transfer)은 다른 일이다

여기가 처음에 제일 헷갈렸다. SMTP라는 이름 하나가 두 가지 일을 가리킨다.

```
썬더버드                Mox                        gmail.com
   |                     |                             |
   |--(1) 제출----------->|                             |
   |   587/465 + 로그인   |                             |
   |                   [큐에 저장]                       |
   |                     |--(2) 전송 25번 포트---------->|
   |                     |    실패하면 재시도            |
```

- **제출** — 내 메일 클라이언트가 "이거 대신 보내줘"라고 서버에 맡기는 것. 인증 필수. 587/465.
- **전송** — 서버가 받는 쪽 도메인의 MX를 조회해서 그 서버 25번 포트로 직접 배달. 인증 없음.

포트가 나뉜 이유가 있다. 25번은 전 세계 아무나 인증 없이 접속할 수 있어야 한다(그래야 메일이 들어온다). 근데 25번에서 "이거 gmail로 보내줘"까지 인증 없이 받아주면 **오픈 릴레이**가 되어 스팸 발송 서버로 악용된다. 그래서 밖으로 나가는 건 인증 필수, 다른 포트로 분리했다.

### "SMTP 클라이언트"는 썬더버드가 아니라 서버 자신

문서의 "SMTP 클라이언트 및 배달 큐"가 헷갈렸던 이유. 메일 서버는 상황에 따라 서버도 되고 클라이언트도 된다.

- 남이 나한테 보낼 때 → 내 서버는 **서버** (25번에서 대기)
- 내가 남한테 보낼 때 → 내 서버는 **클라이언트** (상대 25번으로 접속)

### SMTP는 저장을 안 한다

"그럼 그 대화 내용은 어디 저장되냐"고 물었는데, 답은 "SMTP는 저장하지 않는다"였다.

SMTP 스펙에는 저장 얘기가 아예 없다. 전송 프로토콜이라 "받는 쪽까지 넘긴다"까지가 범위고, 어디에 두는지는 구현하는 사람 마음이다.

SMTP가 정하는 건 **책임 이전 시점** 하나다.

```
DATA
354 Go ahead
...본문...
.
250 OK          ← 이 순간 책임 이전
```

- `250 OK` **전**에 끊기면 → 못 받은 걸로 침. 보낸 쪽이 재시도
- `250 OK` **후**에는 → 받은 쪽 책임. 잃어버리면 안 됨

그래서 "250을 뱉었으면 절대 분실하지 마라"가 유일한 요구사항이고, 그걸 지키려면 250 전에 디스크에 넣어놔야 한다는 결론이 나오는 것뿐이다.

부작용도 있다. 저장은 잘 해놓고 `250` 응답이 유실되면 보낸 쪽은 실패로 알고 재시도한다. 결과는 같은 메일 두 통. SMTP엔 이걸 막을 방법이 없다.

### 봉투 ≠ 편지지 (여기서 모든 사칭이 시작된다)

세션에서 발신자가 두 번 나온다.

```
MAIL FROM:<park@내도메인.com>     ← 봉투. 서버가 실제로 쓰는 값
...
From: 박 <park@내도메인.com>       ← 편지지. 메일 앱 화면에 보이는 값
```

이 둘이 달라도 SMTP는 아무 문제 없이 통과시킨다. 프로토콜에 검증이 없다. 그래서 아무나 `From: ceo@삼성.com`이라고 써서 보낼 수 있고, 이게 피싱의 원리다. 1982년 스펙이라 인증 개념이 없던 시절 물건이다.

### 25번 포트는 IANA(Jon Postel)가 정했다

초창기엔 기관도 아니고 **Jon Postel 한 사람**이 목록 파일을 들고 관리했다. 포트가 필요하면 그 사람한테 메일 보내서 받아가는 식. 그가 펴내던 "Assigned Numbers" RFC 시리즈가 곧 표준이 됐다.

SMTP에 25번이 못박힌 문서가 **RFC 821 (1982년 8월)**, 저자도 Jon Postel이다.

| 범위 | 이름 | 성격 |
|---|---|---|
| 0–1023 | Well-known | IANA 지정. 유닉스에선 root 권한 필요 |
| 1024–49151 | Registered | 신청하면 등록 |
| 49152–65535 | Dynamic | 클라이언트가 임시로 씀 |

## SPF / DKIM / DMARC — 사칭을 막는 세 장치

전부 "SMTP에 인증이 없다"는 구멍을 나중에 메운 것들이다. 각각 답하는 질문이 다르다.

| | 답하는 질문 | 방식 | 메일에 붙어감? |
|---|---|---|---|
| **SPF** | 이 IP가 보낼 자격이 있나 | DNS에 허용 IP 명단 | ❌ DNS에만 |
| **DKIM** | 내용이 위조·변조됐나 | 공개키 전자서명 | ⭕ 서명 헤더 |
| **DMARC** | 화면의 From과 맞나, 안 맞으면 어쩔까 | 위 둘을 묶고 정책 결정 | ❌ DNS에만 |

**메일에 실제로 실려 가는 건 DKIM 서명 하나뿐**이다. SPF는 받는 쪽이 접속해온 IP를 보고 DNS 명단과 대조하는 거라 아무것도 첨부되지 않는다.

### 실물로 보기 (github.com)

```
$ dig +short TXT github.com
"v=spf1 ip4:192.30.252.0/22 include:spf.protection.outlook.com
 include:_netblocks.google.com include:mail.zendesk.com
 include:_spf.salesforce.com include:servers.mcsv.net
 include:mktomail.com include:sendgrid.net ... ~all"
"google-site-verification=82Le34Flgtd15ojYhHlGF_6g72muSjamlMVThBOJpks"
"stripe-verification=f88ef17321660a01bab1660454192e014defa29ba7b8de9633c69d6b4912217f"
"atlassian-domain-verification=jjgw98AKv2aeoYFxiL/VFaoyPkn3undEssTRuMg6C/3Fp/iqhkV4HVV7WjYlVeF8"
... (20개 넘게)
```

`include:`가 잔뜩인 걸 보면 github이 Outlook, SendGrid, Zendesk, Salesforce, Mailchimp를 통해서도 메일을 보낸다는 게 드러난다. **SPF만 봐도 그 회사 메일 인프라가 보인다.**

```
$ dig +short TXT google._domainkey.github.com
"v=DKIM1; k=rsa; p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A..."

$ dig +short TXT _dmarc.github.com
"v=DMARC1; p=quarantine; sp=reject; pct=100; rua=mailto:dmarc@github.com; fo=1"
```

### TXT 레코드는 원래 메모장이었다

DNS는 질문 종류(레코드 타입)마다 답이 다르다. A는 IP, MX는 메일 서버, TXT는 **아무 문자열이나**.

TXT는 원래 사람이 읽는 메모용이었는데, **도메인 주인만 글을 쓸 수 있다**는 성질 때문에 "공증 게시판"으로 전용됐다. 위에서 본 `google-site-verification=`, `stripe-verification=` 같은 게 전부 "이 도메인 진짜 내 것 맞음"을 증명하려고 넣은 것들이다. DNS에 쓸 수 있었다는 것 자체가 소유 증명이다.

용도별로 서브도메인 자리를 이름표로 쓴다.

```
github.com                    ← SPF, 각종 소유확인이 뒤섞임
_dmarc.github.com             ← DMARC 전용 칸
google._domainkey.github.com  ← DKIM 전용 칸
```

`_`로 시작하는 건 "사람이 접속할 호스트가 아니라 기계용 설정"이라는 관례.

여기서 유명한 제약이 나온다. **SPF만 전용 칸 없이 루트에 얹혀 있어서 도메인당 하나만 가질 수 있다.** 그래서 서비스를 여러 개 쓰면 github처럼 `include:`로 한 줄에 다 합쳐야 한다. DKIM은 셀렉터별로 얼마든지 만들 수 있다.

문자열이 중간에 쪼개져 있는 경우가 있는데, DNS TXT 한 덩어리가 **255바이트**를 못 넘어서다. RSA 공개키처럼 긴 값은 항상 잘려 있다.

### DMARC의 "정책"이 무슨 말인가

이게 제일 오래 걸렸다. SPF·DKIM은 검사만 하고 **결과만 뱉는다.** 그 결과로 뭘 할지는 아무도 안 정해줬다.

받는 쪽(gmail) 속마음으로 보면 명확하다.

```
DMARC 없을 때
  "SPF 실패네... 근데 이 도메인이 원래 설정을 안 한 걸 수도 있고,
   전달되면서 깨진 걸 수도 있고... 버렸다 정상 메일이면 사고인데.
   에라 모르겠다, 그냥 배달"

DMARC 있을 때
  "SPF 실패네. _dmarc.도메인 조회해보자... 'p=reject'라고 적혀있네. 버림"
```

**DMARC은 도메인 주인이 그 빈칸을 대신 채워주는 것**이다. "우리는 SPF·DKIM을 100% 붙여서 보내니까, 실패한 건 가짜다"라고.

| 값 | 남한테 내리는 지시 |
|---|---|
| `p=none` | 판단하지 마세요. 리포트만 |
| `p=quarantine` | 스팸함으로 |
| `p=reject` | 아예 받지 마세요 |

내 발등을 찍는 것 같지만, 실제로 걸리는 건 **내 도메인을 사칭한 남의 메일**이다. 그래서 은행·정부·대기업은 거의 다 `p=reject`다.

### DMARC이 추가로 하는 진짜 일 — 정렬(alignment)

SPF·DKIM은 각자 자기 도메인만 볼 뿐, **사용자 화면에 뜨는 `From:`과 아무 연결이 없다.** DMARC이 그걸 연결한다.

이게 왜 중요한지 구체적인 공격으로 보면:

```
공격자가 보낸 피싱 메일

DKIM-Signature: d=공격자.com          ← 자기 도메인으로 정상 서명
From: 보안팀 <security@은행.com>       ← 화면에 뜨는 이름

DKIM 판정:  "서명 유효함" ✓  (거짓말 아님. 공격자.com이 서명한 게 맞음)
DMARC 판정: "서명한 건 공격자.com인데 화면엔 은행.com? 불일치 → 실패"
```

**DKIM은 "서명이 유효한가"만 보지 누가 서명했는지는 안 따진다.** 그걸 From과 맞춰보는 게 DMARC의 알맹이다.

SPF도 마찬가지. SPF는 봉투 도메인만 보는데, DMARC이 "그 봉투 도메인이 화면의 From과 같냐"를 추가로 본다. 둘 중 **하나만** 정렬+통과해도 DMARC pass라, SPF가 전달 때문에 깨져도 DKIM이 살아있으면 통과된다. 서로 약점을 덮어준다.

### 방향이 반대라 헷갈렸던 것

계속 헷갈렸던 게 "누가 게시하고 누가 검증하냐"였는데, 두 그룹의 방향이 정반대다.

| | 게시하는 쪽 | 검증하는 쪽 |
|---|---|---|
| SPF · DKIM · DMARC | **보내는** 도메인 | **받는** 서버 |
| MTA-STS · DANE | **받는** 도메인 | **보내는** 서버 |

앞의 셋은 "내가 누구인지 증명", 뒤의 둘은 "나한테 오는 길 안내"라서 방향이 반대다.

### 여러 도메인을 붙일 때

SPF/DKIM/DMARC은 **서버 단위가 아니라 도메인 단위**다.

```
회사A.com  TXT "v=spf1 ip4:1.2.3.4 -all"   ┐
회사B.com  TXT "v=spf1 ip4:1.2.3.4 -all"   ├─ 전부 같은 서버를 가리킴
회사C.com  TXT "v=spf1 ip4:1.2.3.4 -all"   ┘
```

별도 소유 확인 절차가 있는 게 아니라 **DNS 레코드를 걸 수 있다는 것 자체가 소유 증명**이다. 남의 도메인을 서버에 등록해봐야 껍데기만 생기고 동작하지 않는다.

### A 레코드는 안 건드린다

"구글 워크스페이스 쓰는 회사가 우리 쪽으로 오면 A를 바꿔야 하나?"가 궁금해서 실제 도메인들을 확인해봤다.

```
$ dig +short A stripe.com     → 198.137.150.161      (자기 웹서버)
$ dig +short MX stripe.com    → aspmx.l.google.com   (구글 워크스페이스)

$ dig +short A kakaocorp.com  → 121.53.221.97
$ dig +short MX kakaocorp.com → ps-aspmx3.kakaowork.com
```

**같은 도메인인데 A와 MX가 완전히 다른 곳을 가리킨다.** 도메인 하나가 통으로 움직이는 게 아니라 레코드 한 줄 한 줄이 각각 다른 곳을 가리킬 수 있다.

| 레코드 | 용도 | 이전 대상? |
|---|---|---|
| `회사.com` A | 홈페이지 | ❌ 절대 건드리면 안 됨 |
| `회사.com` MX | 메일 수신 | ⭕ 필수 |
| `회사.com` TXT | SPF·DKIM·DMARC | ⭕ 필수 |

그리고 MX 값에는 **반드시 호스트명**이 들어간다. IP를 직접 못 쓴다. 그래서 이런 구조가 된다.

```
회사.com MX → mail.우리서비스.com → (우리 도메인의 A) → 1.2.3.4
```

우리 도메인에 A를 한 번 만들어두면 고객사는 그 **이름**만 가리키면 되고, 나중에 서버 IP가 바뀌어도 우리 쪽 A 한 줄만 고치면 전 고객사가 자동으로 따라온다.

### MX가 없으면 A로 폴백한다

이건 몰랐던 것. MX 조회 결과가 없으면 SMTP는 **A 레코드의 IP로 25번 접속을 시도**한다(implicit MX). 즉 "MX 없음 = 메일 안 받음"이 아니다.

진짜로 안 받겠다고 선언하려면 **널 MX**를 쓴다.

```
회사.com  MX  0 .
```

메일 안 쓰고 웹사이트만 운영하는 도메인이면 이걸 걸어둬야 사칭 스팸의 반송 메일 폭탄을 안 맞는다.

## STARTTLS — 전송 구간 암호화

### 뭘 "승격"하는 건가

연결을 새로 맺는 게 아니라, **이미 열려 있는 연결을 도중에 암호화로 바꾸는 것**이다.

```
[TCP 연결 맺음]  ← 연결은 하나. 끝까지 이거 하나로 감

220 ready           ← 평문. 도청자에게 다 보임
EHLO test.com       ← 평문
250-STARTTLS        ← 평문
STARTTLS            ← 평문 (마지막 평문)
220 Ready

━━━ 이 지점부터 암호화 ━━━

▓▓▓▓▓▓▓▓▓▓▓         ← 이후 전부 암호화
```

전화 통화 중에 "지금부터 암호로 말하자" 하고 둘 다 암호책을 꺼내는 것. 회선은 그대로다.

왜 이렇게 번거롭냐면, 25번 포트는 1982년부터 전 세계가 평문으로 쓰고 있었기 때문이다. 갑자기 암호화 필수로 바꾸면 기존 서버들이 메일을 못 보낸다. 그래서 "일단 평문으로 만나서 인사하고, 되면 그때 켜자"가 됐다.

### 평문이라는 게 어떤 건가

`nc`로 붙었을 때 화면에 뜬 글자들이 네트워크에 그대로 흘러간 것이다. 도청자가 보는 건 이런 화면이다.

```
MAIL FROM:<park@sender.com>
RCPT TO:<hong@witim.net>
DATA
From: 박 <park@sender.com>
Subject: 계약서 건

말씀하신 대금은 아래 계좌로 부탁드립니다.
국민 123-456-789
.
```

누가 누구에게, 제목이 뭐고, 본문의 계좌번호까지 전부 읽힌다. 암호화되면 랜덤한 바이트 덩어리만 보이고, 알 수 있는 건 "누가 누구 서버에 접속해 몇 바이트 주고받았다" 정도다.

**base64는 암호화가 아니다.** 한글 제목이 `=?UTF-8?B?...?=` 로 보이면 암호처럼 생겼지만 `base64 -d` 한 줄이면 원본이 나온다.

### 구간 암호화지 종단간 암호화가 아니다

```
내 서버 ──🔒──> 네이버 서버 ──> 디스크에 평문 저장 ──🔒──> 받는 사람 앱
       암호화        복호화                          다시 암호화
```

도착하는 순간 복호화되고 저장은 평문이다. 그래서 서버가 스팸 필터를 돌릴 수 있고, 서버 관리자는 마음만 먹으면 읽을 수 있다. TLS가 지켜주는 건 "인터넷을 건너가는 동안" 그 구간뿐이다.

### STARTTLS의 구멍 세 개

1. **협상 실패 시 평문 폴백** — 상대가 TLS를 지원 안 하면 안 보내는 게 아니라 평문으로 보낸다
2. **다운그레이드 공격** — 중간자가 `250-STARTTLS` 한 줄을 지우면 양쪽 다 평문으로 간다
3. **인증서 검증을 안 한다** ← 제일 큼

3번이 핵심이다. TLS는 원래 세 가지를 하는데(암호화 / 인증 / 무결성), 메일 세계는 **인증을 버리고** 썼다.

```
브라우저: 암호화 ✓ 인증 ✓ 무결성 ✓   (인증서 이상하면 빨간 경고창)
메일서버: 암호화 ✓ 인증 ✗ 무결성 ✓   (자체서명·만료·이름불일치 전부 통과)
```

거부하면 메일이 안 가기 때문이다. 인증서가 엉망인 메일 서버가 워낙 많아서 엄격하게 굴면 정상 메일이 대량 유실된다.

근데 인증이 없으면 나머지 둘도 무의미해진다.

```
공격자가 중간에 끼어듦
  → 나와 공격자 사이: 암호화 ✓ 무결성 ✓ (완벽하게 성립)
  → 공격자가 복호화해서 읽고 진짜 서버로 재전송
```

**공격자와 완벽하게 암호화된 통신**을 하고 있는 셈이다. 편지를 완벽한 금고에 넣어 보냈는데 열쇠를 도둑한테 준 격.

## MTA-STS / DANE — 버려진 "인증"을 되살리는 것

둘 다 새 암호화 기술이 아니다. **TLS는 원래 검증할 줄 알았는데 근거가 없어서 못 하던 걸, 근거를 대주는 것**이다.

| | MTA-STS | DANE |
|---|---|---|
| 신뢰 뿌리 | 웹 인증서 (HTTPS) | DNSSEC |
| 정책 위치 | HTTPS 파일 + DNS에 버전 | DNS의 TLSA 레코드 |
| DNSSEC | 불필요 | **필수** |
| 첫 접속 보호 | ❌ (TOFU) | ⭕ |
| CA 필요 | ⭕ | ❌ (자체서명 가능) |
| 운영 사고 위험 | 낮음 | 높음 |
| 주 사용처 | 구글·MS 등 미국 빅테크 | 유럽, 특히 독일 |

### MTA-STS — 진짜 웹서버를 하나 띄운다

"홈페이지에 붙인다"는 게 뭔 소린가 했는데, 말 그대로였다. 정해진 HTTPS 주소에 텍스트 파일을 올려놔야 한다.

```
$ dig +short TXT _mta-sts.google.com
"v=STSv1; id=20210803T010101;"      ← DNS엔 버전 번호만

$ curl -s https://mta-sts.google.com/.well-known/mta-sts.txt
version: STSv1
mode: enforce
mx: smtp.google.com
mx: aspmx.l.google.com
mx: *.aspmx.l.google.com
max_age: 86400
```

브라우저 주소창에 쳐도 그냥 열린다.

**왜 하필 웹서버냐**: DNS는 위조를 막을 방법이 없다. 반면 HTTPS는 이미 인증서로 보호되고 있으니, **새 보안 체계를 만들 필요 없이 기존 웹 인증서 시스템을 재활용**한 것이다.

**mx: 목록이 하는 일**은 내 설정을 검사하는 게 아니라, 못 믿을 경로(DNS)로 받은 답을 믿을 수 있는 경로(HTTPS)로 받은 목록과 대조하는 것이다.

```
공격자가 DNS를 조작해서 회사.com MX → 공격자서버.com 으로 응답

MTA-STS 없으면 → 메일이 공격자한테 배달됨
MTA-STS 있으면 → 정책엔 mail.회사.com 뿐인데? 목록에 없음 → 배달 거부
```

거부하는 주체가 **받는 쪽이 아니라 보내는 쪽 자신**이라는 게 계속 헷갈렸던 부분이다. 구글은 파일 하나 올려둔 것뿐이고, 검사도 거부도 내가 한다. 그리고 본문이 나가기 전(STARTTLS 단계)에 끊기 때문에 메일 내용은 애초에 흘러나가지 않는다.

### TOFU 구멍

정책을 가져오는 과정이 2단계인데 ①이 DNS라 취약하다.

```
① DNS 조회: _mta-sts.회사.com TXT 있나?   ← 여기가 취약
② 있으면 HTTPS로 정책 파일 받아옴          ← 여기는 안전
```

공격자가 ①에서 "그런 거 없는데요"라고 답하면 "MTA-STS 안 쓰는 도메인"으로 취급하고 평문으로 보낸다. 정책 파일 자체는 HTTPS로 보호되지만, **정책이 존재한다는 사실 자체를 숨겨버리면** 파일까지 갈 일이 없다.

한 번이라도 받아오면 `max_age` 동안 캐시하니 그다음부터는 안전하다. 그래서 **첫 접속만** 문제고, 이걸 TOFU(Trust On First Use)라고 한다.

중요한 건 **캐시를 들고 있는 쪽이 보내는 쪽**이라는 것. 구글은 전 세계에서 매초 메일을 받으니 어느 발신 서버든 캐시가 살아있어 틈이 거의 없다. 반대로 어쩌다 한 번 보내는 작은 서버는 매번 캐시가 비어 있어 더 위험하다.

공격 성립 조건이 세 개(캐시 비어있음 + DNS 경로 장악 + 그 타이밍에 메일)라 현실성은 낮다.

### MTA-STS의 근본 한계

받는 쪽 25번 포트는 **평문도 그대로 받아준다.** 강제력은 보내는 쪽에만 있다.

```
MTA-STS 구현한 발신자 → 정책 따름. 평문이면 스스로 포기
MTA-STS 미구현 발신자 → 정책을 모름. 평문으로 들이밀면 받아줌
```

받는 쪽이 평문을 거부할 수도 있지만 아무도 안 한다. 거부하면 그 메일이 사라지는데, 메일 서버 입장에선 "도청당하는 것"보다 "메일 못 받는 것"이 훨씬 큰 사고다. **발신자의 자발적 협조에 의존하는 반쪽짜리**다.

### DANE — DNS에 인증서를 못박음

```
$ dig +short TLSA _25._tcp.mx01.posteo.de
3 1 1 2A2413F46C23290866A3FB9C1658A404BCF6A71373D002A29D67C23ED8DF298D
3 1 1 B2305F6446E9CFAE4F00F0ACC02533EB057C4F2198B6DB068E954D32C1B33EEE
... (5개)
```

세 숫자의 뜻:

| 자리 | 값 | 의미 |
|---|---|---|
| Usage | `3` | 인증서 자체를 못박음. CA 체인 무시 (자체서명 OK) |
| Selector | `1` | 인증서 전체가 아니라 **공개키만** |
| Matching | `1` | SHA-256 해시로 비교 |

일반 TLS는 "이 인증서에 DigiCert 서명이 있나? DigiCert는 믿을 만한가?"를 따지는데, DANE은 **서명을 안 본다.** 그냥 32바이트 두 개가 같은지만 비교한다. 신뢰의 뿌리가 CA에서 DNSSEC으로 옮겨간 것이다.

TLSA가 5개나 걸린 건 키 교체(rollover) 대비 여유분이다.

### DNSSEC이 뭔가

DNS는 원래 아무 검증이 없다. 답이 오면 그냥 믿는다. DNSSEC은 **모든 응답에 전자서명을 붙이고**, 그 서명이 진짜인지는 위 단계가 보증한다.

```
.  (루트)          ← 전 세계가 아는 고정된 키
 └ .de             루트가 "de의 키는 이거 맞음" 보증
    └ posteo.de    de가 "posteo.de의 키는 이거 맞음" 보증
```

인증서 체인과 똑같은 구조다. `DS` 레코드가 그 보증서.

**DANE에 결정적인 능력**: DNSSEC은 "그런 레코드 없습니다"라는 답에도 서명을 요구한다. 그래서 공격자가 "TLSA 없는데요"라고 거짓말을 못 한다. MTA-STS가 뚫리던 지점이 여기서 막힌다.

왜 안 까느냐면 키 관리가 무섭기 때문이다. HTTPS 인증서는 만료돼도 경고창 정도지만, **DNSSEC이 깨지면 도메인 자체가 세상에서 사라진다.**

실제로 확인해보니 갈린다.

```
$ dig +short DS posteo.de   → 53881 8 2 D3D66D1FB310D448...
$ dig +short DS naver.com   → (없음)
$ dig +short DS google.com  → (없음)
```

**구글이 DNSSEC을 안 쓴다.** 그래서 DANE을 못 쓰고 MTA-STS를 만든 것이다. "DNSSEC 없이도 되는 쉬운 버전"이 MTA-STS다.

### DANE의 운영 위험

TLSA에는 만료가 없다. 문제는 **인증서를 갱신할 때** 생긴다.

```
인증서 갱신 → 새 키 생성 → 공개키 바뀜 → 해시 바뀜
           → DNS의 TLSA는 옛 값 → 불일치 → 메일 전면 차단
```

Let's Encrypt는 90일마다 갱신이라 1년에 4번 사고 날 기회가 있다. 우회법은 **키를 재사용하면서 인증서만 갱신**하는 것. Selector가 `1`(공개키만)이라 해시가 안 변한다.

### 국내 현황

```
             STARTTLS  MTA-STS  DANE  DMARC
naver.com       ⭕        ❌      ❌   p=none
daum.net        ⭕        ❌      ❌   p=none
kakao.com       —         ❌      ❌   p=none
```

전부 "암호화는 되는데 강제는 아니고, 사칭 방지는 걸어만 뒀지 효력 없음" 상태다. `p=none`이라 네이버·카카오 사칭 메일이 와도 막으라는 지시가 없다.

규모가 클수록 발신 시스템이 수십~수백 개라 `reject`로 올리면 대량 유실 사고가 난다. 기술 문제가 아니라 **전사 발신 시스템 전수조사** 문제라 몇 년째 `p=none`인 곳이 흔하다.

### SPF/DKIM/DMARC과는 완전히 다른 문제

```
DMARC 완벽 + TLS 없음   → 사칭은 못 하는데 중간에서 내용을 다 훔쳐봄
MTA-STS 완벽 + DMARC 없음 → 도청은 못 하는데 사칭 메일이 암호화된 채로 잘 배달됨
```

| | 막는 것 | 검사 시점 |
|---|---|---|
| SPF / DKIM / DMARC | 남이 내 이름으로 **들어오는** 것 | 메일 다 받고 나서 |
| MTA-STS / DANE | 내 메일이 **새어나가는** 것 | 접속하는 순간 |

## IMAP — 메일함 조작 전담

### IMAP은 메일을 받는 게 아니다

이게 제일 크게 잘못 알고 있던 것.

```
메일이 서버에 도착   → SMTP (25번)
서버에 저장          → 파일 + DB
그걸 열어보기         → IMAP (993번)
```

SMTP가 우편배달부가 우편함에 넣는 것이라면, IMAP은 내가 우편함을 여는 열쇠다. **IMAP을 꺼도 메일 수신은 멀쩡하다.** 클라이언트가 못 붙을 뿐이다.

그리고 IMAP으로는 메일을 못 보낸다. 보내는 명령이 아예 없다. 메일 앱 설정에 "수신 서버"와 "발신 서버"가 따로 있는 게 그래서다. 보낸편지함에 사본이 남는 것도 SMTP가 아니라 앱이 IMAP `APPEND`로 직접 밀어넣는 것이다.

### POP3와의 차이는 "상태가 어디 있냐"

| | POP3 | IMAP |
|---|---|---|
| 원본 | 기기에 다운로드, 서버에서 삭제 | **서버** |
| 읽음/폴더 상태 | 기기마다 따로 | **서버에 저장** |
| 여러 기기 | 폰에서 읽으면 PC엔 안 옴 | 자동 동기화 |
| 부분 다운로드 | 불가 | 가능 |

기기는 서버를 들여다보는 **창**일 뿐이다.

### 실제 CAPABILITY (내 Mox 서버)

```
$ printf 'a1 CAPABILITY\r\na2 LOGOUT\r\n' | openssl s_client -quiet -connect mail.witim.net:993

* OK [CAPABILITY IMAP4rev2 IMAP4rev1 ENABLE LITERAL+ IDLE SASL-IR BINARY
  UNSELECT UIDPLUS ESEARCH SEARCHRES MOVE UTF8=ACCEPT LIST-EXTENDED
  SPECIAL-USE CREATE-SPECIAL-USE LIST-STATUS AUTH=SCRAM-SHA-256-PLUS
  ... CONDSTORE QRESYNC STATUS=SIZE QUOTA METADATA SAVEDATE WITHIN
  NAMESPACE MULTIAPPEND REPLACE PREVIEW MULTISEARCH NOTIFY] mox imap
```

비교로 네이버:

```
* OK [CAPABILITY IMAP4rev1 LITERAL+ SASL-IR ID CHILDREN UIDPLUS
  LIST-EXTENDED SPECIAL-USE UNSELECT QUOTA MOVE AUTH=PLAIN] Naver Imap Server
```

네이버는 `IMAP4rev1`에 확장 12개, Mox는 `IMAP4rev2`에 40개 가까이. 네이버엔 **`IDLE`이 없어서 푸시 알림이 안 된다.** 폴링해야 한다.

- `IMAP4rev2` — 2021년(RFC 9051). rev1이 1996년이니 25년 만의 갱신
- `IDLE` — 연결을 열어둔 채 대기, 새 메일 오면 서버가 즉시 알림. 푸시의 원리
- `CONDSTORE`/`QRESYNC` — "지난번 이후 바뀐 것만" 받아옴
- `SCRAM-SHA-256` — 비밀번호를 네트워크에 안 보내는 인증
- `MOVE` — 예전엔 복사→삭제표시→정리 3단계라 중간에 끊기면 복제되거나 사라졌다

### 상태 머신과 태그

명령마다 쓸 수 있는 상태가 정해져 있다.

```
① 인증 전   CAPABILITY, STARTTLS, LOGIN, AUTHENTICATE
② 인증됨    LIST, CREATE, DELETE, RENAME, STATUS, APPEND, SELECT
③ 폴더 열림 FETCH, SEARCH, STORE, COPY, MOVE, EXPUNGE, IDLE
④ 종료      LOGOUT
```

응답은 세 종류다. `*`(정보, 언제든 끼어듦) / `+`(계속 보내라) / `a4 OK`(그 명령 완료).

### 시퀀스 번호 vs UID — 제일 중요한 함정

```
메일 3통: 시퀀스 1,2,3 / UID 101,102,103
2번을 삭제하면
→ 시퀀스: 1,2  (옛 3번이 2번이 됨!)
→ UID:    101,103 (그대로)
```

시퀀스 번호로 작업하다 그 사이 누가 메일을 지우면 엉뚱한 메일을 건드린다. 그래서 실제 클라이언트는 거의 다 `UID` 접두사를 붙여 쓴다.

`UIDVALIDITY`가 바뀌면 캐시된 UID를 전부 버리고 다시 받아야 한다.

### FETCH — IMAP의 핵심

메시지에서 **원하는 부분만** 가져온다.

| 항목 | 가져오는 것 |
|---|---|
| `ENVELOPE` | 보낸이·받는이·제목·날짜 (파싱된 형태) |
| `BODYSTRUCTURE` | 본문 구조 (파트 구성, 첨부 크기) |
| `BODY[]` | 원문 전체 |
| `BODY[HEADER]` | 헤더만 |
| `BODY[1]` | 1번 파트만 (보통 텍스트 본문) |
| `BODY[]<0.2048>` | 처음 2048바이트만 |

```
목록 그릴 때   UID FETCH 1:* (UID FLAGS ENVELOPE)   ← 본문 안 받음. 빠름
클릭했을 때    UID FETCH 103 (BODYSTRUCTURE)        ← "텍스트 2KB + PDF 8MB"
              UID FETCH 103 BODY[1]                ← 텍스트만. 첨부 안 받음
첨부 눌렀을 때 UID FETCH 103 BODY[2]                ← 그때 첨부만
```

**첨부 20MB짜리도 본문 2KB만 받아서 즉시 표시**할 수 있다. POP3는 통째로 받아야 해서 불가능하다.

`BODY[]`는 읽음 표시를 남기고 `BODY.PEEK[]`는 안 남긴다. 미리보기엔 PEEK를 쓴다.

### 삭제는 2단계

```
UID STORE 103 +FLAGS (\Deleted)   삭제 표시만
EXPUNGE                            실제로 지움
```

**휴지통 개념이 프로토콜에 내장**돼 있다. Gmail 설정의 "자동 삭제 사용 안함 – 클라이언트가 서버를 업데이트할 때까지 대기"가 정확히 이 동작이다.

### 브라우저는 IMAP을 못 쓴다

```
브라우저가 열 수 있는 연결: HTTP / HTTPS / WebSocket   ← 이것뿐
IMAP(993), SMTP(587) → 불가능
```

보안상 브라우저는 임의 포트로 임의 프로토콜 통신을 못 하게 막혀 있다. 그래서 **웹메일은 구조적으로 IMAP을 쓸 수가 없다.**

```
브라우저 ──HTTP(JSON/HTML)──> 웹메일 서버 ──?──> 메일 저장소
          IMAP 없음                        여기엔 있을 수도
```

Roundcube 같은 웹메일은 그 자체로는 메일을 저장하지 않고, **서버에서 IMAP 클라이언트 노릇을 해서** 받아온 걸 HTML로 만들어 보낸다. Mox는 IMAP 서버와 웹메일이 한 프로그램 안이라 저장소를 바로 읽는다.

| | IMAP 직접 사용 |
|---|---|
| 폰 기본 메일 앱 | ⭕ |
| 썬더버드·아웃룩 | ⭕ |
| 브라우저(웹메일) | ❌ HTTP만 |
| Gmail 공식 앱 | ❌ 자체 API |

전용 앱이 표준을 안 쓰는 대신 **Gmail 앱으로는 네이버 메일을 못 본다.** 아이폰 기본 메일 앱은 IMAP만 지원하면 뭐든 붙는다.

### IMAP은 배달 경로에 아무 영향이 없다

한참 헷갈렸던 것. "IMAP 설정하면 우리 서버로 메일이 오게 할 수 있나?" → 안 된다.

```
메일이 어디로 갈지 결정  → MX (DNS)
이미 도착한 메일을 읽기  → IMAP
```

| | 메일이 어디로 도착? | 내 서버가 하는 일 |
|---|---|---|
| IMAP 가져오기 | 구글 | 긁어옴 |
| 전달(forwarding) | 구글 | 사본을 받음 |
| **MX 변경** | **내 서버** | 처음부터 받음 |

`xxx@gmail.com`으로 오는 메일은 무슨 짓을 해도 구글로 간다. `gmail.com`의 MX는 구글 소유다. 목적지를 바꾸는 건 MX뿐이고, 그러려면 주소가 내 도메인이어야 한다.

그리고 전달을 쓰면 **SPF가 깨진다.** 최종 수신 서버가 보는 IP는 gmail IP인데 원발신자 SPF에 그게 있을 리 없다. 다행히 DKIM은 살아남아서 DMARC은 대개 통과한다.

## 실전 점검 — 내 서버에서 찾은 것

배운 걸로 실제 운영 중인 도메인을 찔러봤다.

### MTA-STS가 무효 상태였다

```
$ dig +short TXT _mta-sts.witim.net
"v=STSv1; id=20260513T012136"        ← DNS는 걸려 있음

$ curl -sv https://mta-sts.witim.net/.well-known/mta-sts.txt
* Connected to mta-sts.witim.net (141.164.52.255) port 443   ← 443은 열림
* error: tlsv1 unrecognized name                              ← 그 호스트명을 모름
```

DNS(TXT + CNAME)는 걸어놨는데 **서버에 `mta-sts.witim.net` 이름의 인증서·핸들러가 없다.** 정책 파일을 못 가져오니 발신자들은 "MTA-STS 안 쓰는 도메인"으로 취급하고 평문으로 보낸다.

앞에서 정리한 **"조용한 사고"** 그대로다. 걸어놨다고 생각하지만 실제론 보호가 안 되고, 아무 에러도 안 나서 눈치채기 어렵다.

### PTR이 클라우드 기본값이었다 (수정함)

발신 평판의 기본 관문인데 빠져 있었다.

```
$ dig +short -x 141.164.52.255
141.164.52.255.vultrusercontent.com.     ← Vultr 기본값

$ dig +short A 141.164.52.255.vultrusercontent.com
vultrusercontent.com.
127.0.0.1                                 ← 원래 IP로 안 돌아옴
```

받는 서버는 이렇게 검사한다.

```
① IP → 호스트명 (PTR)      → 141.164.52.255.vultrusercontent.com
② 그 호스트명 → IP (정방향)  → 127.0.0.1
③ ①의 IP와 ②가 같나?       → 불일치
```

이게 **FCrDNS**(정·역방향 일치)인데 깨져 있으면 감점이다. 게다가 `vultrusercontent.com` 같은 클라우드 기본 호스트명은 "임대 서버 = 스팸 발송 가능성" 신호로 읽힌다.

Vultr 콘솔에서 Reverse DNS를 `mail.witim.net`으로 바꾸니 바로 해결됐다.

```
$ dig +short -x 141.164.52.255
mail.witim.net.
```

```
141.164.52.255  →  mail.witim.net       (역방향) ✓
mail.witim.net  →  141.164.52.255       (정방향) ✓
EHLO            →  mail.witim.net       ✓
```

PTR은 웹 서비스엔 영향이 없다. 브라우저는 정방향(도메인→IP)만 조회하고 역방향은 볼 일이 없다. **PTR은 사실상 메일 때문에만 존재하는 설정**이다.

그리고 PTR은 IP당 하나뿐이라, 그 서버에서 여러 도메인 메일이 나가도 대표 이름 하나만 정하면 된다. 받는 쪽은 "PTR이 있고 정·역방향이 일치하나"만 보지 발신 도메인과 같아야 한다고 요구하지 않는다.

Spamhaus는 깨끗했다.

## 발신 평판 (스팸 필터링)

| 요소 | 비중 |
|---|---|
| **수신자 반응** (열람·답장·스팸신고·삭제) | 가장 큼 |
| 도메인 평판 | 큼. IP보다 중요해지는 추세 |
| IP 평판 | 큼. 블랙리스트 등재는 치명적 |
| 인증 통과 (SPF/DKIM/DMARC) | 기본 요건 |
| 인프라 위생 (PTR, TLS, HELO) | 기본 요건 |
| 발송 패턴 | 급증하면 즉시 의심 |

**PTR은 점수를 올리는 게 아니라 0점을 면하는 것**이다. 입장 자격이지 평판 자체가 아니다.

올리는 방법:

1. **기본 위생** — PTR, EHLO 이름, SPF/DKIM/DMARC, STARTTLS
2. **IP 워밍업** — 새 IP는 무평판 = 의심. 하루 50통 → 200통 → 1000통 식으로 몇 주에 걸쳐. 받는 쪽별로 따로 쌓인다
3. **스팸 신고율** — 구글 기준 0.1% 미만. 0.3% 넘으면 위험. `List-Unsubscribe` 헤더를 넣어 "신고" 대신 "수신거부"를 누르게 유도
4. **반송률** — 없는 주소로 보내면 "구매한 리스트 = 스팸" 신호
5. **Google Postmaster Tools** — 구글이 내 도메인을 어떻게 평가하는지 직접 보여준다. 추측 대신 실측
6. **일관성** — 평판은 누적이라 튀는 걸 싫어한다

실무에선 나누기도 한다. 수신은 자체 서버(평판 무관), 대량 발송은 SendGrid·Mailgun 같은 이미 평판 있는 IP를 임대. 아까 github SPF에 `include:sendgrid.net`이 있던 게 그 구조였다.

## 한 줄 요약
SMTP는 1982년에 인증도 암호화도 없이 만들어졌고, SPF/DKIM/DMARC은 "누가 보냈나"를, STARTTLS/MTA-STS/DANE은 "가는 길이 안전한가"를 나중에 덧붙인 것이며, IMAP은 그것과 별개로 도착한 메일함을 열어보는 통로다.
