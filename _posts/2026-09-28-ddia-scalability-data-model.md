## 오늘 공부한 것
『데이터 중심 애플리케이션 설계(DDIA)』 1장 나머지인 확장성과, 2장 앞부분(관계형 모델 vs 문서 모델)을 읽었다. 1장은 "확장성은 공짜가 아니고 뭔가를 내주고 얻는 것"이라는 관점으로, 2장은 지역성과 정규화(ID로 분리하는 이유) 중심으로 정리했다.

## 내가 가졌던 질문
- "확장성이 있다/없다"를 어떻게 판단하나
- 확장성을 얻으려면 무엇을 포기해야 하나
- 튜플은 인덱스인가, 행인가
- 문서 모델이 조회가 빠르다는 건 정확히 무슨 뜻인가 (지역성)
- 문자열을 그냥 넣지 않고 ID로 분리하는 이유
- 문서 DB가 처음엔 편한데 왜 나중에 불리해지나

## 1장 - 확장성(Scalability)

### 1. 확장성의 정의
- 부하(트래픽, 데이터양)가 늘어도 좋은 성능(응답 시간, 처리량)을 유지하기 위한 대처 전략.
- 질문을 바꿔야 한다. "이 시스템은 확장성이 있는가?"가 아니라 **"부하가 X만큼 늘면 시스템을 어떻게 키울 것인가?"**
- 판단 기준은 현재 부하 매개변수(초당 요청 수, 읽기/쓰기 비율 등)와 성능 지표(p95, p99 응답 시간).

### 2. 확장성은 트레이드오프다

| 구분 | 내주는 것 | 내용 |
| :--- | :--- | :--- |
| 확장성 vs 단순성 | 단순성 | 단일 서버/DB에서 샤딩·마이크로서비스로 가면 네트워크 실패, 분산 트랜잭션 등 복잡도가 급상승 |
| 확장성 vs 일관성 | 강한 일관성 | 여러 노드로 나누면 즉시 동기화(ACID) 대신 최종 일관성으로 타협해야 처리량이 나온다 |
| 읽기 vs 쓰기 | 한쪽 성능 | 트위터 타임라인처럼 읽기를 극대화(fan-out 캐싱)하면 쓰기 부하가 늘고, 쓰기를 단순화하면 읽을 때 집계 비용이 커진다 |
| 확장성 vs 인프라 비용 | 돈과 운영 인력 | 캐시, 로드밸런서, 분산 클러스터 비용과 운영 숙련도 요구치가 올라간다 |

### 3. 계층별 대응 전략

**애플리케이션 계층: 무상태 + 수평 확장**
- 비싼 서버 1대로 바꾸는 스케일 업 대신, 범용 인스턴스를 여러 대 늘리는 스케일 아웃.
- 세션 상태를 서버 메모리에 두지 않고 Redis나 JWT 쪽으로 빼야 로드밸런서 뒤에서 인스턴스를 자유롭게 늘리고 줄일 수 있다.

**읽기 분산: 캐시 + 읽기 복제본**
- DB 앞에 Redis, Memcached, CDN을 두고 자주 읽는 건 메모리에서 바로 반환.
- 쓰기는 Primary, 읽기는 Replica들로 나눠 읽기 트래픽을 분산.

**쓰기 분산: 메시지 큐 + 샤딩**
- Kafka, RabbitMQ 같은 큐로 순간 폭증을 버퍼링하고 워커가 순서대로 소비 (스파이크 흡수).
- 단일 DB 용량 한계를 넘으려면 User ID나 해시 기준으로 데이터를 여러 DB 노드에 쪼개 저장.

### 4. 실무 원칙
- 오지도 않을 트래픽을 대비해 처음부터 분산 구조를 넣는 건 개발 속도와 단순성 낭비다.
- 먼저 병목(CPU, 메모리, 네트워크 대역폭, 디스크 I/O)이 어디인지 확인하고, 그 병목에 맞는 확장 패턴을 고른다.

## 2장 - 데이터 모델과 질의 언어

### 1. 관계형 모델
- 1970년 에드가 코드가 제안. 처음엔 은행, 항공 예약 같은 비즈니스 트랜잭션 처리용.
- 핵심은 추상화. 개발자가 디스크 위치(포인터, 경로)를 몰라도 원하는 조건만 SQL로 선언하면 된다.
- 용어 매핑
  - 릴레이션 = 테이블
  - 튜플 = 로우(행, 레코드). **인덱스가 아니라 데이터 한 행**이다. 이론상 순서 없는 집합.
  - 애트리뷰트 = 칼럼

### 2. 객체 관계형 불일치 (Impedance Mismatch)
- 애플리케이션 코드는 객체(트리 구조)를 다루는데 RDBMS는 2차원 표로 저장한다. 그 사이 변환 코드가 계속 생긴다.
- ORM이 이 변환을 줄여주지만, N+1 문제나 불필요한 다중 조인처럼 두 패러다임 차이를 완전히 숨기진 못한다(누수 추상화).

### 3. 지역성(Locality) - 관계형 vs 문서
- 저장소 지역성: 함께 자주 읽히는 데이터가 디스크에 연속으로 모여 있는 성질.

| 구분 | 관계형 (다중 테이블) | 문서 (JSON/JSONB) |
| :--- | :--- | :--- |
| 저장 | `users`, `positions` 등으로 쪼개 저장 | 프로필 트리 전체를 문서 하나에 연속 저장 |
| 조회 | 조인 또는 여러 번 질의 | `user_id`로 한 번에 조회 |
| 지역성 | 낮음 (여러 블록을 오가는 랜덤 I/O) | 높음 (한 번에 순차 읽기) |
| 주의점 | 조인 실수 시 카테시안 곱으로 데이터 뻥튀기, 성능 저하 | 일부만 수정해도 문서 전체를 다시 써야 할 수 있음 |

### 4. 문자열 대신 ID로 분리하는 이유 (다대일, 다대다)
1. **중복 제거, 갱신 편의** - 한 곳에만 저장되니 이름이 바뀌어도 그 레코드 1건만 고치면 참조하는 곳 전부 반영.
2. **모호함 방지** - 오타나 띄어쓰기로 인한 불일치를 막고 검색을 표준화.
3. **현지화** - ID에 붙은 언어별 이름만 바꾸면 다국어 지원이 된다.

### 5. 엔티티 분리와 문서 모델의 한계
- 엔티티: 그냥 문자열이 아니라 고유 ID와 속성(로고, 링크 등)을 가진 독립적인 실체.
  - 예: `"구글"` 문자열 대신 `organizations` 테이블(`id: 101`, `name: "구글"`, `logo_url: ...`)로 빼고 `org_id` 외래키로 참조.
- 문서 DB의 약점
  - 처음엔 조인 없는 일대다 구조라 편하다.
  - 기능이 늘면서 조직, 학교 같은 엔티티 간 참조(다대일, 다대다)가 많아지면 문서 모델이 안 맞기 시작한다.
  - 대부분 문서 DB는 조인 지원이 약해서, 결국 애플리케이션 코드에서 조인을 직접 짜야 한다.

## 한 줄 요약
확장성은 단순성·일관성·비용을 내주고 얻는 것이고, 데이터 모델은 지역성(문서)과 참조 관계(관계형) 중 무엇이 더 중요한지로 고른다.
