## 오늘 공부한 것
『데이터 중심 애플리케이션 설계(DDIA)』 1장. 신뢰성을 해치는 세 가지 결함(하드웨어, 소프트웨어, 사람)과, 성능 쪽에서 나온 지연 시간·백분위 이야기를 읽었다. 읽다가 "노드"가 정확히 뭔지, 우리 서버 구성이 분산 시스템이라고 할 수 있는지도 짚고 넘어갔다.

## 내가 가졌던 질문
- 분산 시스템에서 말하는 "노드"는 정확히 어떤 단위인가
- 서버가 여러 대 있으면 그게 곧 고가용성 분산 시스템인가
- 꼬리 지연은 어떻게 줄이나 (헤지된 요청)

## 정리

### 1. 하드웨어 결함

**결함은 일상이다**
- 디스크 MTTF가 10~50년이어도, 디스크 10,000개짜리 클러스터면 확률상 하루에 1개씩 고장 난다.
- 규모가 커지면 하드웨어 장애는 예외 사고가 아니라 매일 일어나는 일로 전제해야 한다.

**전통적 대응: 장비 1대 안에서 이중화**
- 디스크는 RAID, 전원은 이중 전원 장치·UPS·예비 디젤 발전기, CPU는 핫 스왑.
- 부품 하나가 죽어도 서버가 안 죽게 해서 수년간 무중단 가동.

**현대: 소프트웨어 내결함성으로 이동**
- 데이터와 연산이 커지면서 여러 장비를 쓰는 애플리케이션이 늘었다.
- AWS 같은 클라우드는 개별 인스턴스의 신뢰성보다 유연성·탄력성을 우선한다. 인스턴스가 예고 없이 사라지거나 재부팅되는 게 흔하다.
- 그래서 "머신은 언제든 죽는다"를 전제로, 장비 손실을 소프트웨어 레벨에서 견디게 설계하는 쪽으로 바뀌었다.

**덤으로 얻는 운영상 이점: 순회식 업그레이드(Rolling Update)**
- 단일 서버: OS 패치, 커널 업데이트로 재부팅하면 계획된 다운타임이 생긴다.
- 다중 노드: 한 대씩 트래픽에서 빼고 패치·재부팅 후 다시 넣는 식으로 무중단 운영이 가능하다.

### 2. 노드란 무엇인가

- 클러스터를 구성하는 **컴퓨터 1대 또는 가상 서버 인스턴스 1개** 단위.
- 맥락에 따라 가리키는 게 다르다.
  - 웹/애플리케이션 계층: 로드 밸런서 뒤에 무상태로 떠 있는 API 서버 인스턴스
  - 스토리지/DB 계층: 데이터를 저장하고 복제본(replica)을 유지하는 DB·캐시 서버
- 서버가 여러 대 있다고 고가용성 분산 시스템이 되는 건 아니다. API, DB, 스트리밍처럼 **역할을 1대씩 나눠 맡은 구조는 사실상 단일 서버 여러 개**일 뿐이다. 어느 한 대만 죽어도 서비스 전체에 장애가 번진다(SPOF가 역할마다 있는 셈).

### 3. 소프트웨어 오류 (체계적 오류)

**하드웨어 결함과 뭐가 다른가**
- 하드웨어: 랙 온도 같은 공통 원인이 없으면 장비마다 **독립적으로** 고장 난다. 1번 디스크가 죽는다고 2번이 같이 죽진 않는다.
- 소프트웨어: 모든 노드에 **같은 버전**이 깔려 있어서 노드 간 상관관계가 높다. 특정 입력 하나로 수십~수백 대가 한꺼번에 죽을 수 있다.

**주요 유형**
- 동시 중단 버그: 특정 입력에 모든 인스턴스가 동시에 크래시 (예: 2012년 6월 30일 리눅스 커널 윤초 버그)
- 공유 자원 고갈: 한 프로세스가 CPU·메모리·디스크를 독점해 서버 전체가 마비
- 응답 지연: 시스템이 느려져 타임아웃
- 연쇄 장애(cascading failure): 작은 결함이 다른 구성 요소로 번져 도미노처럼 무너짐

**원인과 대응**
- 원인: 개발자가 당연하게 여긴 환경 가정("시간은 항상 증가한다", "외부 응답은 1초 안에 온다")이 특수 상황에서 깨질 때.
- 대응
  - 시스템 가정과 컴포넌트 상호작용을 꼼꼼히 검토
  - 엣지 케이스까지 포함한 테스트
  - 프로세스 격리: 한 프로세스 장애가 다른 데로 안 번지게
  - 죽은 프로세스 자동 재시작
  - 모니터링·알림 (예: 메시지 큐 송수신 건수 추적)

### 4. 인적 오류

- 대규모 인터넷 서비스 연구에 따르면 중단 원인에서 하드웨어 결함은 10~25% 정도고, **운영자의 설정·조작 실수**가 훨씬 크다.
- "실수하지 마라"가 아니라 **실수해도 프로덕션이 안 깨지는 구조**를 만드는 게 답이다.
  - 테스트/스테이징/프로덕션 샌드박스 분리
  - 빠른 롤백
  - 세분화된 권한 관리, 작업 검증 자동화

### 세 가지 결함 비교

| 구분 | 하드웨어 결함 | 소프트웨어 오류 | 인적 오류 |
| :--- | :--- | :--- | :--- |
| 발생 특성 | 부품별 독립적, 확률적 | 전체 노드 동시 발생 (상관관계 높음) | 설정 오타, 잘못된 배포·명령 |
| 영향 | 단일 노드 손실 | 서버 수와 무관하게 전체 마비 | 시스템 중단의 주원인 |
| 대응 | 다중화, 분산 내결함성 설계 | 테스트, 프로세스 격리, 모니터링, 자동 재시작 | 권한 제어, 샌드박스, 점진적 롤아웃, 빠른 롤백 |

### 5. 성능: 지연 시간과 백분위

**선두 차단(Head-of-Line Blocking)**
- 앞의 무거운 요청이 늦어지면 뒤에 온 가벼운 요청까지 대기열에 갇힌다.
- 그래서 서버 내부 처리 시간만이 아니라 **클라이언트가 체감하는 지연**을 재야 한다.

**꼬리 지연 증폭(Tail Latency Amplification)**
- 화면 하나를 위해 여러 백엔드를 병렬 호출하면, 최종 응답 시간은 **가장 느린 호출**이 결정한다.
- 개별 서비스의 p99가 괜찮아도 병렬 호출 수가 늘수록 사용자가 느린 응답을 겪을 확률이 급격히 커진다.

**헤지된 요청(Hedged Requests)**
- 첫 번째 복제본에 요청을 보내고 일정 시간(예: 50ms) 안에 응답이 없으면, 같은 데이터를 가진 다른 복제본에도 같은 읽기 요청을 보내 먼저 오는 응답을 쓴다.
- 부작용을 피하려고 읽기 전용 작업에만 쓴다.

**모니터링 주의점**
- 실시간 백분위 계산은 HdrHistogram, t-digest 같은 알고리즘으로 메모리·CPU를 아낀다.
- **백분위끼리 평균 내면 안 된다.** 순서 기반 지표라서, 합치려면 히스토그램을 병합해야 한다.

### 6. 설계 우선순위

- 부하 특성은 제각각이다. 1kB 요청 초당 10만 건과 2GB 요청 분당 3건은 전혀 다른 구조가 필요하다.
- 오지도 않은 대용량 트래픽을 상상해서 복잡한 분산 구조를 미리 넣으면 엔지니어링 낭비와 유지보수 부담만 늘어난다.
- 초기 제품은 가상의 부하 대비보다 **빨리 기능을 만들고 시장 피드백으로 고치는 게 먼저**다.
