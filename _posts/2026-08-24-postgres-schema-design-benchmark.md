## 오늘 공부한 것

ERD 설계 자료를 모으다가 "이렇게 짜면 성능이 얼마나 좋아지는지"를 정리하고 싶어졌다. 블로그 글 인용만으로는 못 믿겠어서 로컬에 PostgreSQL 17.8 인스턴스를 띄우고 직접 쟀다.

처음엔 실험 10개 정도로 시작했는데, 재는 방법 자체를 세 번 틀렸다. 그걸 고치는 과정이 실제 수치보다 더 배울 게 많았다. 마지막엔 전체를 7회 반복해서 "이 차이가 진짜인가"를 판정했고, 거기서 내가 앞서 써둔 주장 3개가 틀린 게 드러났다.

- 환경: PostgreSQL 17.8 (Homebrew), Apple Silicon, `shared_buffers 512MB`, `fsync=off`
- 최종: 42개 실험 × 7패스 = 262회 실행, 측정 1,011행

`fsync=off`라 쓰기 절대값은 실제보다 빠르다. 설계 A와 B의 **비교**로만 쓸 수 있는 수치다.

## 내가 가졌던 질문

- 조회수를 게시글 행에 UPDATE 하면 안 된다던데, 얼마나 나쁜가
- UUID를 PK로 쓰면 느리다는데 몇 배나
- 소프트 딜리트의 진짜 비용은 뭔가
- 복합 인덱스는 정말 "선택도 높은 컬럼을 앞에" 둬야 하나
- EAV는 왜 쓰면 안 되나
- 파티셔닝은 몇 행부터 해야 하나
- 그리고: 내가 잰 이 숫자들을 믿어도 되나

## 정리 (Q&A 핵심)

### 재는 방법을 세 번 틀렸다

**1. `DO $$ LOOP $$` 안에서 UPDATE 10만 번 → 156초**

카운터 컬럼 갱신 비용을 재려고 plpgsql 루프를 돌렸다. 1회당 1.56ms가 나왔다. 너무 느려서 이상했다.

원인은 **전부 단일 트랜잭션**이라는 것. 같은 행을 반복 갱신하면 튜플 버전 체인이 계속 길어지고, 트랜잭션이 안 끝나니 죽은 튜블을 회수할 수도 없다. 실제 서비스는 요청마다 커밋한다.

`pgbench`로 다시 쟀더니 **108,000 TPS**가 나왔다. 100배 넘게 과장하고 있었다.

**2. `shared_buffers 512MB`에서 UUID 벤치 → uuid4와 uuid7 차이가 0**

100만 행 삽입에서 uuid4 1,696ms, uuid7 1,547ms. 시간순 UUID가 빨라야 하는데 차이가 없었다.

인덱스가 통째로 캐시에 들어가서다. **UUID 페널티는 CPU가 아니라 I/O 페널티**라, I/O가 없으면 차이도 없다.

`shared_buffers`를 16MB로 줄이고 300만 행으로 다시:

| PK 타입 | 삽입 | PK 인덱스 | 리프 채움률 |
|---|---:|---:|---:|
| bigint | 2.0초 | 64MB | 90.1% |
| uuid4 | **8.8초 (4.4배)** | 122MB | 67.0% |
| uuid7 | 4.7초 (2.3배) | 120MB | 67.7% |

여기서 하나 더 알았다. **uuid7은 리프 페이지 채움률을 개선하지 못한다.** 같은 밀리초 안에 수천 건이 들어오면 그 안에서는 여전히 무작위라 페이지 분할은 그대로 일어난다. uuid7의 이득은 페이지 packing이 아니라 **삽입이 인덱스 끝부분에만 몰려 캐시 적중률이 오르는 것**이다.

**3. 커버링 인덱스가 안 먹었다**

`INCLUDE`를 붙인 인덱스와 안 붙인 인덱스가 똑같이 0.9ms로 나왔다. Index Only Scan이 안 잡혔다.

visibility map을 확인해보니 `relallvisible`이 1,671 / 14,706 — **11%만 채워져 있었다.**

벌크 적재 직후 **첫 VACUUM은 페이지를 all-visible로 표시하지 못한다.** 삽입 트랜잭션이 아직 xmin horizon 안에 있어서다. 두 번 돌리니 100%가 됐고, 그제야:

```
1차 VACUUM: VM  11%  → Bitmap Heap Scan, 0.9ms, 1,483블록
2차 VACUUM: VM 100%  → Index Only Scan,  0.1ms,   154블록
```

`settle()` 헬퍼를 만들어 VACUUM을 두 번 돌리게 고정했다.

### 7회 반복이 알려준 것

시간을 채우려고 전체 스위트를 7번 반복했는데, 실제 값어치는 **지표별 재현성**이었다.

| 지표 | 변동계수(중앙값) |
|---|---:|
| 테이블·인덱스 크기, **읽은 블록**, HOT 비율, 행 수 | **0%** |
| 리프 채움률 | 0.5% |
| TPS, 지연 | 8~9% |
| 조회·집계·삽입 시간 | 10~19% |

**크기와 블록 수는 완벽하게 재현되고, 시간은 안 된다.** 그래서 정리할 때 방침을 바꿨다 — 가능하면 시간이 아니라 **읽은 블록**으로 근거를 댄다. 블록 수는 플래너가 실제로 만진 페이지 수라 기계가 달라져도 같다.

### 그리고 내 주장 3개가 틀렸다

**EAV 50배 → 실제 1,700배**

상품 20만 개 × 속성 8개에 `color=red AND size=m`을 걸었다.

| 방식 | 저장 | 조회 | 읽은 블록 |
|---|---:|---:|---:|
| 정규 컬럼 | 21.1MB | 0.029ms | 97 |
| JSONB + GIN | 43.9MB | 1.04ms | 148 |
| EAV | 179.9MB | 50.4ms | **1,016,229** |

처음에 정규 컬럼을 `0.0ms`로 반올림해 표시해놓고 **그 값으로 배수를 계산**했다. 실제는 0.029ms라 격차는 50배가 아니라 1,700배였다. 반올림한 값으로 나눗셈하면 안 된다는 걸 몸으로 배웠다.

**`numeric`이 `bigint`보다 1.2배 느리다 → 노이즈였다**

단일 측정에서 45.2ms vs 37.3ms가 나와서 "numeric은 가변 정밀도라 CPU를 더 쓴다"고 썼다. 7패스로 보니 62.6ms vs 56.6ms에 변동계수가 17%/39%, 범위가 겹쳤다.

저장 크기는 둘 다 127.4MB로 동일했다. **성능을 이유로 numeric을 피할 근거는 없다**로 결론을 바꿨다. 다통화나 부가세 배분이 있으면 그냥 numeric 쓰면 된다.

**복합 인덱스 선행 컬럼 13배 → 시간으로는 범위가 겹친다**

`(tenant_id, status)`와 `(status, tenant_id)`에 `tenant_id`만 걸어봤다. 시간은 1.6ms vs 23.8ms인데 변동계수가 각각 55.8%/42.9%로 범위가 살짝 겹쳤다.

블록으로 보니 **2,691 vs 58,936 — 일관되게 21.9배**. 결론은 유지하되 근거를 블록으로 바꿨다.

덤으로 "선택도 높은 컬럼을 앞에 두라"는 조언도 검증했다. **두 컬럼을 모두 `=`로 거는 쿼리에서는 순서가 아무 상관 없다** (0.07ms로 동일, 블록 1,461 vs 1,464). 진짜 규칙은 선택도 순이 아니라 **"항상 WHERE에 들어가는 컬럼을 앞에"**다.

### 나머지 결과 중 인상 깊었던 것

**카운터 컬럼 — 문제는 카운터가 아니라 인덱스였다**

게시글 1만 건에 흩뿌려 갱신하면 본문 행에 그냥 UPDATE 해도 108k TPS에 HOT 업데이트 100%가 나온다. 멀쩡하다.

그런데 **카운터에 인덱스를 하나 걸면** HOT 비율 100% → **0%**, 죽은 튜플 171만 개, 테이블 +59.6MB. 인덱스된 컬럼을 UPDATE 하면 HOT이 불가능해지고 매번 인덱스 엔트리를 새로 만든다.

샤딩은 조건부다. 부하가 흩어지면 오히려 손해(16클라이언트에서 본문행 126k vs 샤딩 110k)고, **한 행에 몰릴 때만** 뒤집힌다. 32클라이언트가 같은 행을 때리면 단일 행은 8c의 68.5k에서 **37.6k로 역전 하락**하는데 16조각 샤딩은 90.6k를 유지한다.

**파티셔닝은 조회가 아니라 삭제 때문에 한다**

적재는 파티션이 10~23% 느리고, 조회 이득은 인덱스가 이미 가져가서 거의 없었다(8M에서 14.8ms vs 14.0ms).

갈리는 건 삭제다. 8M에서 한 달치를 지울 때:

```
DELETE  420ms ~ 19,302ms   (변동계수 119%)
DROP    136ms ~    231ms   (변동계수  22%)
```

중앙값 배수는 17.9배인데, 더 중요한 건 **`DELETE`가 46배나 흔들린다**는 것이다. 죽은 튜플 상태와 autovacuum 타이밍에 좌우된다. 운영에서 무서운 건 느린 것보다 **언제 느려질지 모르는 것**이다.

**외래키 — 삽입보다 삭제가 위험하다**

100만 건 삽입이 FK 없음 0.9초 → FK 있음 3.9초(4.5배). 이건 감수할 만하다.

진짜 문제는 삭제다. 자식 테이블의 FK 컬럼에 인덱스가 없으면 부모 삭제가 **19.5ms → 1,455ms (75배)**. PostgreSQL은 자식 FK 컬럼에 인덱스를 자동으로 만들어주지 않는다. 직접 만들어야 한다.

**컬럼 선언 순서만 바꿔서 21% 절약**

같은 8개 컬럼, 같은 200만 행인데 177.6MB vs 146.1MB. 행당 88 → 66바이트.

`int`/`bigint`/`smallint`를 번갈아 선언하면 8바이트 정렬 경계를 맞추려고 패딩이 낀다. **넓은 타입부터 좁은 타입 순**으로 선언하면 된다. 참고로 NULL은 거의 공짜다 — text 컬럼 10개를 전부 NULL로 채운 테이블이 행당 40바이트였다.

**TOAST — 위험한 건 큰 텍스트가 아니라 중간 크기 컬럼**

본문 4,000자를 넣으면 힙이 오히려 작아진다(500자 279MB vs 4,000자 48.2MB). TOAST가 2KB 넘는 값을 빼가고 힙에는 포인터만 남기기 때문이다.

문제는 **500자짜리**다. TOAST 임계값에 못 미쳐 힙에 눌러앉고, `tenant_id`만 세는 집계에도 279MB를 다 읽어야 한다. 300~2,000자짜리 설명·주소·메모가 위험 구간이다.

**Hash 인덱스는 쓸 이유가 없었다**

같은 300만 행에서 등치 조회: B-tree 0.18ms / 20.1MB vs Hash 3.97ms / **134.7MB**. 6.7배 크고 21배 느리다.

BRIN은 반대로 흥미로웠다. B-tree보다 42% 느린데 **인덱스 크기가 사실상 0**이다. 적재 순서와 값 순서가 일치하는 시계열 로그에서는 쓸모가 있겠다.

그리고 **GIN 두 개가 조용히 무시당하고 있었다.** 배열·JSONB 조건의 선택도가 25%라 플래너가 인덱스를 버리고 Seq Scan을 골랐다. 같은 GIN인데 전문검색(선택도 0.02%)은 1.13ms로 잘 돈다. **인덱스를 만들었다고 쓰이는 게 아니다.**

### 하네스도 한 번 갈아엎었다

처음 스크립트는 테이블을 만들고 안 지웠다. 47개가 쌓여서 pgdata가 10GB가 됐고, 디스크가 96%까지 찼다.

고친 방식: 실험마다 스키마 하나를 만들고, **끝나면 드롭하기 전에 전체 인벤토리를 기록**한 뒤 `DROP SCHEMA CASCADE`.

```
피크 디스크  누적 7,074MB → 단일 실험 1,180MB   (전체 순증 5MB)
```

남기는 것: `runlog.jsonl`(측정 + 드롭 직전 인벤토리, append-only) · `disk-log.jsonl` · `plans/*.txt`(EXPLAIN 전문) · 디스크 가드 · 실험 단위 재개.

그리고 검사기를 하나 만들었다. **본문에 쓴 숫자가 측정 데이터에 실제로 있는지 확인하는 테스트**다. 재측정할 때마다 낡은 숫자를 잡아냈는데, 처음엔 굵은 글씨만 검사해서 놓친 게 많았고 범위를 넓히니 17개가 걸렸다.

## 아직 헷갈리는 것 / 다음에 볼 것

- `fsync=off`로 쟀다. 실제 디스크 flush가 들어가면 쓰기 쪽 비율이 어떻게 바뀔지 모르겠다
- 파티션 개수를 늘리면 플래닝 비용이 언제부터 문제가 되는지 — 12개까지만 해봤다
- 커넥션 풀, 리플리카 지연은 아예 안 건드렸다
- 한국어 전문검색(`mecab-ko`)은 설치를 안 해서 못 쟀다
- 12M 행 구간은 디스크가 모자라 일부 건너뛰었다. 더 큰 규모에서 곡선이 어떻게 되는지 확인하고 싶다

## 한 줄 요약

스키마 설계 성능은 직접 재봐야 알 수 있고, **재는 방법이 틀리면 100배까지 과장되며, 같은 실험을 여러 번 돌려보기 전까지는 시간 수치를 근거로 쓰면 안 된다.**
