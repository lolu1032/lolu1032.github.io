## 🌐 1. 웹 & 네트워크 기본기

### Q1. 브라우저 주소창에 `https://naver.com`을 치면 일어나는 일
1. **DNS 조회**: 브라우저/OS 캐시를 확인하고, 없으면 DNS 서버에 질의하여 도메인을 IP 주소(`223.130.195.95`)로 변환합니다.
2. **TCP 3-Way Handshake (4계층)**: 신뢰성 있는 연결을 위해 클라이언트와 서버가 3번 패킷을 주고받습니다.
   * `SYN` (연결 요청) ➡️ `SYN-ACK` (요청 수락 및 확인) ➡️ `ACK` (최종 확인)
3. **TLS/SSL Handshake (보안 계층)**: HTTPS 통신을 위해 공개키/비밀키 방식으로 대칭키를 안전하게 교환하고 세션을 암호화합니다.
4. **HTTP 요청 및 응답**: 브라우저가 `GET /` HTTP 요청을 전송하고, 서버가 HTML/CSS/JS를 응답(200 OK)합니다.
5. **브라우저 렌더링**: HTML 파싱(DOM 트리) + CSS 파싱(CSSOM 트리) ➡️ 렌더 트리 결합 ➡️ 레이아웃(크기/위치 계산) ➡️ 페인팅(화면 그리기).

### Q2. ICMP(Ping)와 TCP SYN의 결정적 차이
* **차이점**:
  * **ICMP (3계층/네트워크)**: 포트 번호가 없습니다. 단순히 "그 서버 IP 장비가 살아있는가(Ping)"만 확인합니다. 많은 클라우드 방화벽이 Ping은 열어두고 서비스 포트는 막는 경우가 흔합니다.
  * **TCP SYN (4계층/전송)**: **특정 포트(80, 443 등)**에 접속을 요청하는 첫 패킷입니다.
* **실무 트러블슈팅 사례**:
  > "서버 IP로 핑(ICMP)을 쳤을 때는 응답이 오는데, 웹 포트(80/443)로 보낸 TCP SYN 패킷에는 SYN-ACK 응답이 0건이었습니다. 즉, 서버 하드웨어 자체는 살아있으나, 서버 앞단의 방화벽이나 인프라 네트워크 단에서 포트가 차단되었다는 명백한 증거를 찾아 호스팅사에 전달해 해결했습니다."

### Q3. HTTP 상태 코드 & 멱등성(Idempotency)
* **상태 코드 핵심**:
  * `200 OK` (성공), `201 Created` (생성 성공)
  * `301 / 302` (리다이렉트: 영구 이동 / 임시 이동)
  * `400 Bad Request` (요청 문법 오류)
  * `401 Unauthorized` (인증 안 됨, 로그인 필요) vs `403 Forbidden` (인증은 됐으나 권한 없음)
  * `404 Not Found` (리소스 없음)
  * `500 Internal Server Error` (서버 코드 에러)
  * `502 Bad Gateway` (앞단 Nginx/프록시가 뒷단 백엔드 앱 연결 실패)
  * `504 Gateway Timeout` (뒷단 처리 지연으로 프록시 타임아웃)
* **HTTP 메서드와 멱등성**:
  * **멱등성**: 연산을 여러 번 수행해도 결과가 달라지지 않는 성질.
  * `GET`, `PUT`, `DELETE`: **멱등함** (GET을 10번 하든, DELETE를 10번 하든 결과 상태는 동일).
  * `POST`: **비멱등함** (호출할 때마다 새 주문/게시글이 중복 생성됨).

## ⚙️ 2. JavaScript / TypeScript & Node.js 기본기

### Q4. Node.js는 싱글 스레드인데 어떻게 많은 요청을 동시에 처리하나요? (이벤트 루프)
* **핵심**: Node.js는 **싱글 스레드 이벤트 루프** 기반이지만, 무거운 작업(파일 I/O, 네트워크 통신, 암호화)은 백그라운드의 **libuv 스레드 풀(Thread Pool)**에 넘겨 비동기로 처리합니다.
* **이벤트 루프의 동작 순서**:
  1. 동기 코드는 **Call Stack**에서 즉시 실행.
  2. 비동기 작업(API 호출, DB 쿼리)이 완료되면 콜백이 **Queue**에 쌓임.
  3. **Call Stack이 완전히 비었을 때**, 이벤트 루프가 큐에서 콜백을 꺼내 스택으로 올려 실행함.
  4. ⚠️ **우선순위**: `Promise.then` 같은 **Microtask Queue**가 `setTimeout` 같은 일반 Macrotask Queue보다 무조건 먼저 실행됩니다.

### Q5. TypeScript를 쓰는 이유
1. **정적 타입 검사**: 자바스크립트는 런타임에 `undefined is not a function` 같은 에러가 터지지만, 타입스크립트는 컴파일 단계(코드 칠 때)에서 오타와 타입 불일치를 사전에 잡아냅니다.
2. **협업과 자동 완성**: 객체 안에 어떤 필드가 들어있는지 IDE가 자동 완성을 지원하여 API 스펙 파악 시간이 획기적으로 줄어듭니다.

## 🗄️ 3. 데이터베이스 & PostgreSQL 기본기

### Q6. 인덱스(Index)는 무엇이고 왜 쓰며, 왜 무작정 많이 걸면 안 되나요?
* **개념**: 책 맨 뒤의 **'색인(찾아보기)'**입니다. 기본적으로 **B-Tree(Balanced Tree)** 구조를 사용합니다.
* **장점**: 수백만 건의 데이터에서도 테이블 전체를 스캔(`Seq Scan`)하지 않고 `O(log N)` 속도로 빠르게 검색(`Index Scan`)합니다.
* **단점**: 데이터를 `INSERT`, `UPDATE`, `DELETE` 할 때마다 인덱스 트리도 재정렬해야 하므로 **쓰기 성능이 저하**됩니다.

---

### Q7. PostgreSQL의 HOT(Heap-Only Tuples) 업데이트란?
* **설명**:
  * PostgreSQL은 행을 수정(`UPDATE`)할 때 기존 행을 덮어쓰지 않고, 새 행을 블록에 쓰고 옛 행을 삭제 표시하는 **MVCC 구조**를 가집니다.
  * 이때 **인덱스가 걸려있지 않은 컬럼**을 수정하면, 인덱스는 그대로 두고 데이터 블록 내에서만 포인터로 연결하는 초고속 최적화를 수행하는데, 이를 **HOT 업데이트**라고 합니다.
  * 하지만 **조회수, 카운터처럼 자주 바뀌는 컬럼에 인덱스를 걸어버리면**, 1씩 증가할 때마다 인덱스까지 전부 다시 써야 하므로 HOT가 깨지고 디스크 I/O가 폭증합니다.

---

### Q8. 부모 테이블 행을 지울 때 자식 FK에 인덱스가 없으면 일어나는 참사
* **설명**: `orders(주문)` 부모 테이블과 `order_items(주문상품)` 자식 테이블이 있을 때, 부모의 한 주문을 삭제하면 DB는 자식 테이블에 연결된 상품이 있는지 검사해야 합니다.
* **문제**: 자식 테이블의 `order_id` 외래키(FK) 컬럼에 인덱스가 없으면, 자식 테이블 **수천만 건 전체를 풀스캔(Seq Scan)**하게 되고 부모/자식 테이블 전체에 락(Lock)이 걸려 서비스가 멈춥니다.
* **해결**: 외래키(FK) 컬럼에는 반드시 인덱스를 생성해야 합니다.

## 🛡️ 4. 실무 안전장치 & 아키텍처 패턴

### Q9. 구독 결제에서 "타임아웃 시 결과를 모를 때 닫지 않는다"는 원칙
* **상황**: 고객 결제 요청 후 PG사 응답을 기다리는데 네트워크 타임아웃이 발생함.
* **설계 원칙**:
  1. 결제 상태를 즉시 실패로 닫지 않고 `PENDING(승인 확인 중)` 상태로 유지.
  2. 주문번호(Idempotency Key)를 기반으로 백그라운드에서 PG사 원장 조회 API를 단건 호출.
  3. PG사에서 실제로 승인되었으면 `PAID(완료)`로 확정, 승인 내역이 없으면 그때 안전하게 `FAILED(실패)` 처리.

---

### Q10. 대량 발송(SMS/알림톡)에서 보상 트랜잭션과 안전장치
* **상황**: 외부 문자 발송 API는 성공했는데, 내 로컬 DB 저장 도중 서버 오류 발생.
* **보상 트랜잭션**:
  * 로컬 DB 트랜잭션과 외부 HTTP 통신은 단일 트랜잭션으로 묶을 수 없습니다.
  * 발송 상태를 `SENDING`으로 먼저 기록하고, 외부 API 호출 결과 응답을 받아 `SUCCESS`로 업데이트합니다.
  * 만약 외부 호출이 실패하거나 예외가 발생하면, 즉시 작업을 되돌리거나 관리자 큐에 알림을 전송하는 보상 로직을 구성합니다.
* **안전장치**:
  * 템플릿 변수(예: `#{고객명}`) 미입력 시 발송 차단 유효성 검사.
  * 테스트 발송 기본 강제화 및 1회 최대 발송 상한 설정.

---

### Q11. LLM 호출 지문(Fingerprint) 캐싱
* **상황**: LLM API 호출 비용과 응답 지연 최적화.
* **구현**:
  * 요청 파라미터(텍스트, 모델, 옵션 등)를 정렬된 JSON으로 만들어 **SHA-256 해시값(지문)**을 생성.
  * 이 지문을 캐시 키(Key)로 Redis/DB에 조회하여, 이전 결과가 존재하면 API를 호출하지 않고 기존 결과를 재사용해 **비용 0원 & 응답 시간 0초** 달성.

### Q12. 브라우저 자동화에서 휴먼인더루프(Human-in-the-loop)
* **설계**:
  * 반복적이고 시간이 오래 걸리는 서류 작성 및 데이터 입력은 자동화 스크립트가 전담.
  * 계정 잠금 위험이 있는 로그인과 법적 책임/수수료가 발생하는 최종 제출 단계만 사람에게 남겨두는 **휴먼인더루프** 구조로 안정성 확보.
